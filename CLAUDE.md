# CLAUDE.md

Static recompilation of **Ridge Racer 7** (PlayStation 3, USA, `BLUS30001`, version 01.02) to native code. Same requirements and scope as the sister projects (Qilin1066/GBTGhoulies--QilinRecomp, ApbArcade--QilinRecomp, RhythmHeavenFever--QilinRecomp, PunchOutWii--QilinRecomp, WindWakerHD--QilinRecomp), down to the same settings menu. This repository is Qilin1066/RidgeRacer7--QilinRecomp (two hyphens). The claude.ai Project "Ridge Racer 7 Recomp" holds a short status note (`claude/status.md`); this file and `docs/` are the full record.

## Requirements (non-negotiable)

- **Efficiency first, then accuracy, and fail loudly.** Never paper over an unknown: stop with a clear error (an error message and exit code in the tools, `rt::Stop` in the runtime, CMake `FATAL_ERROR`).
- **C++23** everywhere: recompiler, runtime and generated code.
- **Vulkan 1.3 only** for graphics. No OpenGL, D3D or Metal backends (macOS goes through MoltenVK).
- **Static recompilation only.** No interpreter, JIT or emulator at runtime, not even as a fallback. This covers the **SPU programs** and the game's **shaders** too: both are translated at build time.
- Targets: 64-bit **Windows, Linux, macOS** on **x86-64 and ARM64**. The low-end reference is ARM boards like the **Raspberry Pi 4** (whether it can hold this game's frame rate is open: measure, don't promise). No iPadOS, no 32-bit.
- Compiler minimums: GCC 14, Clang 19, Apple Clang (Xcode 16), MSVC 2022 17.10.
- **No PS3 keys, ever**, in the repository or the tools: `EBOOT.BIN` is not decrypted here. (The 16-byte suffix of the import-id hash is not a key and is in `import_names.cpp`, by the owner's decision.) The player decrypts their own with RPCS3 (`docs/elf-analysis.md`).
- Nothing copied from an emulator (RPCS3 is GPL-2.0 and the behaviour reference: run, not read) and no code of other people's copied in. Third-party libraries are fetched by CMake at configure time, pinned, never committed (SDL3, the Vulkan headers and volk, Dear ImGui, when the window arrives, as in the other recomps). Keep dependencies to the fewest possible (the owner's standing preference). The project itself is GPL-3.0, as all the QilinRecomp projects are since 2026-11-21.
- Never commit game data or anything derived from it: `EBOOT.BIN`, `EBOOT.elf`, `PARAM.SFO`, `analysis-out/`, listings, import lists, lifted code. These are gitignored. Facts about the program written up in `docs/` (sizes, counts, hashes) are fine, as in the sister projects.

## Layout

- `recomp/src/`: `elf` (the PS3 program: segments, sections, the entry descriptor, process and PRX parameters, imports with ids, slots and stubs, exports, TLS), `self` (`EBOOT.BIN`'s plain header: the ELF's tables, the stored segments, the SDK library stamps), `sfo` (`PARAM.SFO`), `title` (finds the files in the player's copy; `known_build`; the decrypt message), `media` (the headers of the `.nub` sound banks and `.pam` films), `spu_image` (the SPU programs inside the program), `import_names` (id to name, all 248; `import_id`), `syscall_names` (number to name, all 78), `sha256`, `bytes.hpp`. These are CMake's `qilin_game`: **runtime code too, so no `std::format` in them** (macOS 10.15). `ppu` (the PPU decoder, `qilin::ppu`), `spu` (the SPU decoder, `qilin::spu`), `spu_cfg` (the SPU control-flow pass) , `cfg` (the control-flow pass, with the `.eh_frame` and exception-table readers), `archive` (`RR7.DAT`'s directory, from the program) , `shaders` (the compiled Cg programs in the program) and `lift` (the PPU lifter) are CMake's `qilin_recomp`: tools only, as is `main.cpp`, the `qilin` CLI (`std::format` and `std::print` are fine there).
- `recomp/tests/`: `tests.cpp` (unit tests), `elf_builder.hpp` (builds a program, its SELF and a `PARAM.SFO` in memory), `difftest/` (`gen.cpp` lifts random encodings at build time, `ref.cpp` is the separately written reference interpreter, `run.cpp` compares them: `qilin_difftest`, in `ctest`).
- `runtime/`: CMake's `qilin_rt`, what lifted code compiles against: `include/qilin/rt/cpu.hpp` (the CPU state, memory access, the helpers lifted code calls), `fp.hpp` (bit-exact floating point), `vmx.hpp` (VMX; included by `cpu.hpp`), `memory` (the 4 GiB address space). **Runtime code: no `std::format`.**
- `tools/analyse-game.ps1` and `Analyse game.bat`: build `qilin` on Windows and write the analysis to `analysis-out/`. Keep the script Windows PowerShell 5.1-compatible and ASCII-only. Run on the owner's PC up to the decrypt message; its steps after that (imports, exports, profile) have not run.
- `tools/check/verify_decoder.py`: the PPU decoder against GNU objdump (`--sweep` in CI; `--game` needs the decrypted program and a PowerPC objdump). `tools/check/verify_spu_decoder.py`: the SPU decoder against binutils 2.31.1's `spu-elf-objdump`, which CI builds from source and caches (`OBJDUMP_SPU`).
- `docs/`: design and results. Keep them current. `runtime.md` the runtime and what it provides; `roadmap-and-design-targets.md` is the roadmap and every design decision (open ones are marked **open**); `elf-analysis.md` the program and what has been read from the owner's disc; `data-files.md` the sound banks, films and archive; `recompiler-core.md` the decoder and its check; `prior-art.md` what may be taken from where; `naming.md` the names.
- `ridgeracer7/src/`: the game. `machine` (CMake's `ridgeracer7_machine`, built always: memory, the first thread, the hooks, the import and system-call boundary), `imports.cpp` and `syscalls.cpp` (which gather each file's table of what is provided natively, by name and number), `kernel` (error codes, object tables by id, guest memory for native code), and one file for each part of the system: `sync`, `sync_calls`, `threads`, `events`, `timers`, `memory`, `mempool`, `sysutil`, `video`, `gcm` (cellGcmSys) and `rsx` (the RSX's thread and its table of state methods), `font` (cellFont on FreeType), `fs` (cellFs: the mount points), `gamedata`, `spurs`, `net` and `np` (no cable, not signed in), `pad`, `usbd`, `tty`, `spu`; `fault` (the report of a bad memory access). To add a function: write it in its file, add it to that file's table; a new file also needs a line in `machine.hpp`, in `imports.cpp` or `syscalls.cpp`, and in CMake. `main.cpp` (the `ridgeracer7` executable, which exists only when CMake is given `-DQILIN_GEN_DIR=<lifted code>`). **Runtime code: no `std::format`** (`rt::log`, `rt::fatal` are printf-style).
- `tools/build-ridgeracer7.ps1`: builds `qilin`, lifts the owner's copy into `build-game/gen`, builds `ridgeracer7`. By hand in the usual `build` folder: `build\Release\qilin.exe lift <game> --out build\gen`, `cmake -S . -B build -DQILIN_GEN_DIR=<repo>\build\gen`, `cmake --build build --config Release --target ridgeracer7`, then `build\Release\ridgeracer7.exe <game>`.
- `host/`: the other Qilin recomps' host layer (WindWakerHD's, with this game's names: `qilin/ridgeracer7`, `RIDGERACER7_SAVE_DIR`): window and events (SDL3), Vulkan through volk, presentation, frame times. `host/src/shaders.inc` is generated by `tools/build_shaders.py` (CI checks it). Keep it in step with the sister projects'. The game doesn't use it yet.
- Still to come, in WindWakerHD--QilinRecomp's layout: `settings`, `menu` (Dear ImGui, when the menu arrives), the rest of the system libraries.

## Known facts worth not rediscovering

- The owner's copy is the disc's folder on the owner's PC, outside the repository (its path is in the claude.ai Project's `claude/status.md`; local paths are not written here). `RR7.DAT` is 5.23 GB and `BGM.nub` and `ending.pam` are over 600 MB: a cloud session can stage files of up to 400 MB, so those never leave the PC whole. `EBOOT.BIN` (7.8 MB) and `PARAM.SFO` stage fine, and so will `EBOOT.elf`.
- **`EBOOT.elf` exists** (since 2026-11-21, v0.3.0), beside `EBOOT.BIN` on the owner's PC: SHA-256 `689f9704ee9dbd982c48de646f07d69c193a46513d75b6f95f20a206c7754831`, 7,818,800 bytes. It was made there by a session that installed RPCS3 0.0.43 at the owner's request (the official Windows build, in a folder `RPCS3` beside the game's, outside the repository) and ran `rpcs3.exe --decrypt <EBOOT.BIN>`: no set-up, no firmware, a few seconds. The loader read it with nothing to fix.
- RPCS3's ELF has zeros where the SELF's non-segment sections were: **no section names, no `.comment`, no SDK stamps** (those come from the SELF). `elf.section("name")` finds nothing on the real file: find sections by address, flags or content. Section names in `docs/elf-analysis.md` stay inferred from name lengths.
- The real program (`docs/elf-analysis.md`): 99.47% of 1,065,028 code words decode, the rest are jump tables of signed offsets after `bcctr` (291 runs) and constants; 151 instructions used; no `lwarx`/`stwcx.`, no `dcbz`; 502 `sc` sites, 78 system calls by a backwards scan for `li r11` (25 sites unresolved); 42 SPU programs at `0x10052b00` (41 SPURS-shaped at `0x3000`, entry `0x3010`; `bnusCoreSpu.elf` at `0x80`), 209,492 words, the car's physics among them, GCC 4.0.2.
- A cloud session reaches the PC only while the Claude desktop app is open there, and can run commands there only when the app offers its shell (`device_bash`). In the session that made v0.1.0 it offered listing and staging files, not the shell: nothing was run on the owner's PC, and the owner's sister-project folders were read by staging files.
- Tags don't reach GitHub from a cloud session (the proxy refuses pushing them: HTTP 403); `main` does. Releases are marked by their commit's title (`vX.Y.Z: ...`) and the changelog until a tag can be pushed from elsewhere.
- The cloud workspace has GCC 13 and Clang 18, both below the minimums: build there with zig's Clang (`pip install --break-system-packages ziglang==0.17.1`, then wrapper scripts running `python3 -m ziglang cc` / `c++` as `CMAKE_C_COMPILER` / `CMAKE_CXX_COMPILER`). It has no PowerPC objdump: a decoder sweep runs in CI.
- The SELF (`EBOOT.BIN`, SHA-256 `095ed6cb8e90538309b57662fb19da1ba2c4bdbac5fd40dc0be6122e76d4c0db`): header `0x980` bytes, then the ELF's file image at the same offsets plus `0x980`. The five loaded segments are encrypted; so are `.comment` and the section name table, though they lie outside every segment. The section headers and the SDK stamp list (section 33) are plain. Section names in `docs/elf-analysis.md` are inferred from name lengths: replace them when the ELF is read.
- The SELF's SDK version header (at the offset the extended header gives): type, present, size `0x30`, then at `+0x20` the stamp list's offset in the file and at `+0x28` its length. The stamps run together with no separators ("crt0:p102002crt1:p102002..."): a name, a colon, one letter and digits.
- `PARAM.SFO`'s `SOUND_FORMAT`: the compressed formats are two bits each sharing bit 1 (Dolby Digital `0x102`, DTS `0x202`); this disc's 263 is LPCM 2.0, LPCM 5.1 and Dolby Digital.
- An extraction of the owner's `.7z` was still running when the first session listed the folder (`RR7.DAT` showed 36 MB with a fresh date, and two films were missing). A file with today's date among 2006 ones is a file still being written: list again before recording sizes.
- A local session on the owner's PC (Claude Code there) has the shell, MSVC 19.44, CMake, Python 3.12 and `gh`, and can push to `main` directly (pushing a tag from there hasn't been tried). It has **no PowerPC objdump**, no WSL and no Docker: the decoder's check against binutils runs only in CI, so push and read the sweep's log (`gh run view <id> --log`). Git has no identity set there: commit as the first commit did (`git -c user.name=Claude -c user.email=noreply@anthropic.com commit`), which also keeps the owner's name out.
- The data files, read on the owner's PC (`docs/data-files.md`): films are PAMF `0041` with MPEG-2 video (not AVC) and, in three, ATRAC3plus; `BGM.nub` is ATRAC3plus 5.1 at 48 kHz, `Game_DJ.nub` 16-bit big-endian mono PCM. `RR7.DAT` has no directory at its start (its first `0x360` bytes are zero, then a compressed file): the directory is probably in the program. Reading all 5.2 GB of it in Python takes about two minutes there.
- The game's code, as the control-flow pass found it (`docs/recompiler-core.md`): every function has a descriptor (ELFv1 ABI), all with TOC `0x4de880`; most code is built with a small TOC per file (`lwz r30, d(r2)` in the prologue, then constants at `d(r30)`), so a switch's table address is two loads deep; jump tables are 32-bit offsets from the table's own address, straight after the `bctr`; `.eh_frame` uses pc-relative 8-byte addresses (`0x14`), 7,530 FDEs; **C++ exceptions are in real use** (2,845 landing pads, reachable only through `.gcc_except_table`); inlined system calls set `r11` before a branch, so the number needs dataflow, not a look at the line above.
- Another session may push to `main` at the same time (one did on 2026-11-21): `git fetch` and rebase before pushing, never force.
- A bash heredoc passed through the tool loses `\\n` escapes in Python source: write edit scripts to the scratchpad as files.
- The lifter (`docs/recompiler-core.md`): 64-bit mode semantics, 32-bit effective addresses, registers in locals synced at `@OUT@`/`@IN@` placeholders (WindWakerHD's scheme). When adding an instruction to the slice: a case in `lift.cpp`, a helper in `cpu.hpp` if it needs one, a case in `ref.cpp` written from the definition and not from the helper, and `in_slice`; the generator picks it up by itself. Check a change can fail the test by breaking it once on purpose. Undefined results (divide by zero, `mulhw`'s upper half, `mfocrf`'s other fields) are stated choices in `cpu.hpp`. MSVC warns (C4324) on `alignas` members of `Cpu`: warnings are errors.
- Floating point (`fp.hpp`, `docs/recompiler-core.md`): never use the host's single-precision `fma` (not every C library's rounds once); a product of two singles is exact in a double; for anything rounded twice use the error's sign and `single_from` (round to odd); beware error terms that underflow (the one fault the reference found). `-ffp-contract=off` (set in CMake for GCC and Clang) is what keeps the error-free transformations honest: generated code must be built with it too. Round to nearest is assumed and the FPSCR's flags aren't kept, so FPSCR instructions stay out of the slice.
- VMX (`vmx.hpp`): a register is `Vec{uint32_t w[4]}`, element 0 first; **non-Java mode is assumed** (`kNonJava`: denormals are zeros), from public descriptions, as is the NaN order vA, vB, vC: both to be confirmed against RPCS3. `vrefp`/`vrsqrtefp` are the **correctly rounded** 1/x and 1/sqrt(x): a stated choice within the architecture's bound (the PPU's own tables aren't known; they'd replace it).
- The runtime's loop of work (`docs/runtime.md`): run `ridgeracer7`, read the one line it stops with (an import by name, a system call by number, an unlifted function by reason), provide that properly in `imports.cpp` or `syscalls.cpp`, rebuild (seconds: the lifted files don't change), repeat. Never answer a call with a guess to get further. The first build of the lifted code took 14 minutes on the owner's PC before `/MP`.
- The system, as the game uses it (read off its code, `docs/runtime.md`): `sys_event_queue_receive` returns its event in `r4`-`r7`; a thread's entry is a descriptor (code, TOC); the game prints through `sys_tty_write`; it loads system modules `0x1e`, `0x19`, `0x1b`, `0x1a`, `0x1c`, `0x9`, `0`, `0x16`. The process ends by `std::_Exit` (guest threads may be running: nothing is torn down under them). **The scheduler is not as designed yet**: guest threads run freely; suspect it first when something looks like a race.
- The owner's PC has a PS3's system software installed by RPCS3 (2026-11-21, at the owner's word): Sony's `PS3UPDAT.PUP` (in a folder `firmware` beside the game's) installed with `rpcs3 --headless --installfw`, giving `RPCS3/dev_flash/data/font` (the console's fonts, which `ridgeracer7` finds there by itself). Never commit any of it.
- Finding a fault: a crash prints the guest address and the lifted functions on the stack (`fault.cpp`); lift with `qilin lift <game> --out build\gen --pc` to have it name the instruction (the local `build/gen` is lifted that way during bring-up; `tools/build-ridgeracer7.ps1` doesn't). `RR7_WATCH=<seconds>` shows where each guest thread is; `RR7_RSX_SURVEY` lists RSX methods not provided. A run that prints nothing and exits with no `stopped:` line used to be a silent crash: pipe to a file and read the exit code.
- The game's threads greet by posting a semaphore and then waiting on it: waking order matters (semaphores hand a post to the longest waiter). Expect the same of mutexes and conditions when something looks like a race.
- The RSX (`rsx.cpp`): state methods are a table (`kState`), acting methods a switch; an unknown method stops the game. Flips are two private methods (`0xE940`, `0xE944`). `NV406E_SET_REFERENCE` is `0x50`.
- All 42 SPU programs end with `stop 0x102` (the system's SPU-thread exit) and are built as plain SPU threads; the game also starts SPURS (4 SPUs, four tasksets) through a wrapper of its own around `0x11c000`-`0x11e000` that has both back ends. The game's hard-disk folder is `BLJS10001` (the Japanese id; the hard disk is `dev_hdd0` in the port's data folder). To read a word or string of the program's data: `python <scratchpad>/peek.py`-style, by the ELF's program headers.
- What the system hands the first thread (read off the start-up code): `r3`-`r5` arguments, `r7` thread id, `r8`-`r10` the thread-local image's address, file size and memory size, `r12` the heap's page size. Thread-local variables are at `r13 - 0x7000 + offset`.
- `qilin lift <game> --out <folder>` writes all lifted code (derived from the game: outside the repository). Compiling all of it with MSVC takes about three minutes with `/w /bigobj`.
- The decoders are written without reading binutils' source (it is the independent check: run, not read). SPU objdump's conventions, learnt from the sweep: registers `$3`, channels `$ch3`, `# hex` comments after operands above 16, `stop` with no operand, bits 11–13 of indirect branches, `sync` and `hbr` as mnemonic suffixes (`p`/`c`, `d`, `e`), and no check of any bit outside the opcode.
- binutils' `cell` set differs from the PPU in reviewed ways (`docs/recompiler-core.md`): it has `lq`/`stq`, `attn`, `eciwx`/`ecowx` and the supervisor's instructions, and ignores several reserved bits. objdump's raw mode prints every optional operand (`sc 0`, `bclr 20,lt,0`, `lwarx r3,0,r4,0`, `mfcr r3,-1`).
- Other PS3 static recompilations exist (`docs/prior-art.md`: ps3recomp and ports built on it). Their licences are unchecked: don't read their code until they are.
- Facts about the game not read from the disc (60 frames a second, 1080p, online play, what it shares with Ridge Racer 6) are from public descriptions.
