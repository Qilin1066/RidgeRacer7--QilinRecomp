# The recompiler's core

The parts of `qilin` that turn the game's code into C++: decoders, control-flow passes, lifters. So far (v0.10.0): the decoders and control-flow passes for both processors, and the PPU lifter for 96% of the game's code, all run on the game's code.

## The PPU decoder (`recomp/src/ppu.*`, `qilin::ppu`)

The PPU is the Cell's PowerPC core. It implements the 64-bit PowerPC architecture (version 2.02), the vector extension (VMX, or AltiVec), and eight vector loads and stores of its own for unaligned data (`lvlx`, `lvrx`, `stvlx`, `stvrx` and their `l` forms). Every instruction is one big-endian word.

The decoder has the shape of the other Qilin recompilers' (PunchOutWii's and WindWakerHD's decode the 32-bit 750): **one row per base mnemonic** with its opcode bits and operand fields, and tables built from the rows when the program starts.

- **383 instructions.** `Rc` ("."), `OE` ("o"), `LK` ("l") and `AA` ("a") are bits of an instruction, not separate entries.
- **Every bit a row doesn't define must be zero.** Reserved bits set decode as invalid, and so do invalid forms: a load with update whose base is its target or is absent, `lmw` and `lswi` loading over their own base, a branch whose `BO` has a reserved bit set, `bcctr` decrementing the counter, `mfocrf` and `mtocrf` naming other than one field, `mftb` of anything but the time base, a fourth kind of `sync`.
- **The supervisor's instructions are not in the table** (the MSR, the segment and translation tables, `rfid`, `dcbi`): a PS3 program runs in user mode. Nor are instructions the PPU doesn't have (`lq`, `stq`, `eciwx`, `ecowx`, the 970's `dcbzl`). Any of them in the game's code is an invalid word, and the recompiler stops on it.
- Two rows may share an extended opcode where a higher bit tells them apart (`mfcr` and `mfocrf`, `mtcrf` and `mtocrf`, `dst` and `dstt`, `dss` and `dssall`): the table chains them, and building it fails if two rows could match the same word.
- Each row carries the properties the passes go by: branch, load, store, floating point, VMX, cache hint, synchronisation, and `k64` for the instructions that work on all 64 bits of a register where a 32-bit twin does not.

What differs from the Nintendo recomps' decoder: 64-bit forms (`ld`, `std`, `lwa` and their 14-bit displacements; the `rld*` rotates with six-bit shifts and masks; `sradi`; `mulld`, `divd`; `fcfid`, `fctid`), compares with an `L` bit, `BO` under version 2's rules (hint bits `a` and `t`, where the 32-bit architecture had `y`), `bclr` and `bcctr` with a `BH` field, `sync` with a kind (`lwsync` is `sync 1`), `dcbt` with a `TH` field, no paired singles, and VMX: opcode 4 with 11-bit, 10-bit (the compares, whose record bit is bit 21) and 6-bit extended opcodes.

The text form follows GNU objdump's `-M cell,raw`: no simplified mnemonics (`blr` is `bclr 20,lt,0`, `mr` is `or`, `li` is `addi rD,0,n`), so two decoders can be compared as text.

Addresses are 32 bits wide, as an LV2 process's are: a branch target wraps at 4 GB.

### Checked against binutils

`tools/check/verify_decoder.py` compares the decoder with GNU objdump word by word: the mnemonic and every operand must match, and a word must be valid for both or for neither.

With binutils 2.42: **4,931,891 words; 4,266,210 valid and identical; 539,096 invalid for both; no unexplained disagreement.**
- `--game <game>`: every word of the game's code sections. *Not run yet: the decrypted program is on the owner's PC, which has no PowerPC objdump, and CI has no game.*

**Not settled by the sweep**, because binutils can't say what the PPU itself does:

- `dcbzl`, `mcrxr`, `ldbrx` and `stdbrx`: whether the PPU has them is from public descriptions. The first is left out and the other three are in. **None of it matters to this game**: its code uses none of the four, nor `dcbz` (v0.3.0).
- `vspltb`, `vsplth` and `vspltw` take an element number of 4, 3 and 2 bits, as binutils has them; the bits above are reserved here.
- `dcbt` and `dcbtst` accept any `TH`: a prefetch hint changes nothing the program can see.

### The commands

```sh
build/qilin cfg     <game>                  # the control-flow pass's report
build/qilin insns   <game>                  # every word of the code: address, word, instruction
build/qilin profile <game>                  # how often each instruction is used; what doesn't decode
build/qilin disasm  <file> [--base 0x10000] # a file of raw big-endian words, as insns prints them
```

`insns` and `profile` read the decrypted program's executable sections. On the real program (v0.3.0, `elf-analysis.md`): 1,065,028 words, 99.47% of which decode; the rest are jump tables and constants lying in the code. The game uses **151 of the 383 instructions**, which is the lifter's work list: a narrow, floating-point part of VMX, no atomic sequences, no cache instructions but `dcbt`.

## The control-flow pass (`recomp/src/cfg.*`, `qilin cfg`)

Finds every function, follows every branch, and accounts for every word of the code. **On the game: 1,065,028 words, none unknown.**

| | |
|---|---|
| Functions | 14,294: the entry point, 248 import stubs, 14,045 from descriptors. One round: no function is found only by a call or a tail call |
| Code | 1,059,387 words reached |
| Jump tables | 5,634 words in 296 switches |
| Padding | 3 words |
| Dead | 4 words: an epilogue after a trap that always fires |
| Unknown | **0** |
| Words reached that aren't instructions, branches out of the code | 0 |

What the program gives, and the pass takes:

- **Descriptors.** In this ABI every function has one (14,046 of them, in one section, each a code address and the one TOC, `0x4de880`), so they are the list of functions. The section is found as the one holding the entry point's descriptor: RPCS3's file has no section names.
- **Unwinding tables** (`.eh_frame`, found by its content): 170 CIEs and 7,530 FDEs, each FDE the exact first and last address of a function. A function with one is explored to that end; one without (the C library's, mostly) to the next function's start.
- **Exception tables** (`.gcc_except_table`): 932 functions have one, with **2,845 landing pads** between them: the places the C++ unwinder enters a function when an exception passes through it, to run destructors or a `catch`. Nothing branches to a landing pad, so without these tables 51,000 words of code look unreachable. They are entry points of their functions.
- **Import stubs**: the 248, each ending in the `bctr` that enters the system. A call to one is a call to a named system function.

What it works out:

- **Switches.** GCC puts a switch's table in the code, straight after the `bctr`, as 32-bit offsets from the table's own address. The table's address is loaded from a table of constants: the TOC itself, or (most of the game's code, built with a small TOC per source file) the file's own table, whose address the function takes from the TOC into a register in its prologue. The pass reads both from the file. All 296 tables are found, and all lie straight after their `bctr`. **The size of 293 is proven** (264 until after v0.13.0) by the bound the code checks the index against: `cmplwi` and `bgt` to the default on the way in, or the switch's block entered only by `cmplwi` and `ble`, or by `bgt` to the default followed by `b` into it. The compare may be anywhere above its branch on the straight line (the compiler hoists it past the register saves), and the search stops at anything else that writes the same CR field (another compare, `fcmpu`, a CR logical operation, `mcrf`, `mtcrf`, a record form into that field). A block that starts straight after another switch's table counts as entered only by its branches. Unit tests hold each rule, including that a write to the same field loses the proof. The other 3 (`0x4162ec`, `0x419624`, `0x41b8f4`: the out-of-range index goes through a call that doesn't return) were sized by where their targets begin (a table ends where the nearest thing it jumps to starts) until after v0.13.1, when the pass learnt which functions never return (below): **all 296 are proven**, and the sizes didn't change. The two methods agree on every table that has both, and a wrong size would leave unknown words or reach words that aren't instructions: there are none of either.
- **System calls.** The number is the value of `r11` at the `sc`. The compiler usually sets it just above, sometimes before a branch or a join, so the pass follows the constant in `r11` along every path through the function. **All 502 sites are numbered: 78 different system calls** (`elf-analysis.md`).
- **Tail calls**: a branch out of a function. Here every target was already a function.
- **Open-ended functions**: 491 reach their end without a return or a jump, because they end in a call that doesn't return (a throw, `abort`, `exit`). All but 18 have an unwinding entry that says where they end, and those 18 each end in a call and the `nop` after it.
- 4,943 indirect calls (`bctrl`), and no indirect jump that isn't a switch or an import stub.

**What this means for the runtime.** The game uses C++ exceptions for real: its unwinder and personality routine are part of the lifted code, and they resume a function at a landing pad with registers they have restored. So a lifted function has more than one way in (its start and its landing pads), and the lifted unwinder's jump to a landing pad must reach the right one. How the lifter does it (after v0.13.1): "C++ exceptions" under the PPU lifter, below. Every landing pad lies in the part of its function that starts at the function's unwinding entry (`qilin cfg` says how many don't: none), which the lifter needs.

**Functions that never return** (after v0.13.1). After the rounds that find functions, the pass works out which never return to their caller: the least set of functions that can return, grown until nothing more joins it. A function can return if some way through it, from its start or from one of its landing pads (an exception caught there may end in a return), reaches a return without passing a call of a function outside the set. What isn't known counts as a way back: a jump through CTR that isn't a switch, a tail call to something that isn't a function, a word that isn't an instruction. Import stubs return, but for the two imports that end the process and the thread (`sys_process_exit`, `sys_ppu_thread_exit`); a function that only loops, or returns only through a call of itself, never does. If the set changed, the pass runs another round, in which a switch's block entered from above only by a call of a function that never returns (`bl abort; nop` straight before it) counts as entered only by its branches. **On the game: 47 functions never return, and the last 3 switches are proven: 296 of 296** (their out-of-range index calls `0x3fc5c0`, which writes a message and calls `sys_process_exit`); found in 2 rounds, still in under half a second, the coverage unchanged. Unit tests hold each rule (a loop, the exit import and the same stub under another name, a return on one path, a jump through CTR, a call of a function that never returns), and fail when the rule is taken out.

Not done yet: a JSON output for the lifter; data pointers into code other than descriptors (none are needed for coverage, but vtables point at descriptors, not code, which is worth confirming).

## The SPU decoder (`recomp/src/spu.*`, `qilin::spu`)

An SPU is not a PowerPC: 128 registers of 128 bits, no condition register, 256 KiB of memory of its own, channels to the rest of the machine. Every instruction is one big-endian word whose opcode is its first 4, 7, 8, 9, 10 or 11 bits.

- **199 instructions**, one row each (mnemonic, the opcode and its length, the form, properties), in the PPU decoder's shape. Building the table fails if two opcodes overlap.
- **Every bit an instruction doesn't define must be zero**, as in the PPU decoder: `clz` with its unused register field set, or `lnop` with anything set, is an invalid word.
- The text follows objdump's: registers are `$3`, channels `$ch29`, a load is `lqd $3,16($1)`, a branch names the address it reaches, and bits 11 to 13 of the indirect branches, `sync` and `hbr` show in the mnemonic (`bid`, `bie`, `syncc`, `hbrp`). `stop` prints without its signal type, as objdump's does (the decoder has it).

### Checked against binutils 2.31.1

The roadmap's open question was the reference: binutils dropped the SPU after its 2.3x line, so no distribution packages an SPU objdump. **CI builds one**: binutils 2.31.1's source from the GNU server, pinned by SHA-256, configured for `spu-elf`, and kept in a cache. `tools/check/verify_spu_decoder.py` compares the decoder with it word by word.

- `--sweep` (in CI, on every push): 48 random words for each of the 2,048 values of the first 11 bits, then every single-bit neighbour of every word either decoder accepted. **1,664,400 words; 1,476,288 valid and identical; 151,494 invalid for both; none unexplained.**
- binutils decodes by the opcode alone and ignores every other bit. So for a word qilin rejects, the check asks qilin again to look past reserved bits (`spu-disasm --ignore-reserved`), and if that reading is objdump's, counts it apart: 36,618 words, "reserved bits set". There is no other rule: nothing else differs.
- The decoder was written from the published instruction set without the reference at hand (binutils' source is not read, only run). The sweep's first run found no fault in any opcode or field, only the two matters of text above.
- `--game <game>`: every word of the game's SPU code. *Not run: no SPU objdump where the game is.*

### On the game's SPU programs

`qilin spu-profile`: the 42 programs' **209,492 words; 209,488 decode**. The other four are the one jump table in all of the SPU code (four addresses after a `bi`, in the sound core).

- **147 of the 199 instructions are used.** The most frequent: `lqd`, `il`, `stqd`, `shufb`, `ai`, `ori`, `rotqby`, `lqx`: loads, constants and shuffles, as SPU code is. So `spu.hpp`'s `shufb` builds a word at a time from picks read straight from the source words, and the byte shifts and rotates (`rotqby` and its kin) work on the register as two 64-bit halves (checked against the byte-at-a-time versions they replaced on 21 million cases, and by the differential test).
- **Floating point is single precision**: `fma` (3,690), `fm`, `fs`, `fcgt`, `fnms`, `fa`, the estimates (`frest`, `frsqest` with `fi`). Double precision appears in two programs only (`dfm`, `dfs`, `dfa`, 219 words), and the double fused forms and compares not at all.
- **5,547 channel writes and 845 reads**: the programs talk to the system through channels (memory transfers, signals, the mailboxes), which is what the runtime has to provide in place of an SPU's hardware.
- 4,714 branch hints (`hbra`, `hbr`, `hbrr`): no effect on what a program computes; the lifter drops them.
- 87 `stop` and 8 `stopd`; `heqi` (331) and `hlgti` (41) are the compiler's traps.
- Not used: `bra`, `brasl`, `iret`, `bisled`, interrupts in general, `sync`, the special-purpose registers, the byte-wise compares and averages, most halfword rotates.

## The SPU control-flow pass (`recomp/src/spu_cfg.*`, `qilin spu-cfg`)

The same job as the PPU pass, on each of the 42 SPU programs. **Every word accounted for: 209,492 words, none unknown.**

| | |
|---|---|
| Functions | 2,332 |
| found by the entry point | 42 |
| by direct calls (`brsl`) | 1,256 |
| by tail calls (a branch out of a function) | 197 |
| by an address loaded with `ila`, or held in data | 23 and 84 |
| by nothing: unreferenced code at a clean boundary | 730 |
| Code | 208,634 words |
| Jump-table entries | 4 |
| Padding (`nop`, `lnop`, zero) | 854 |
| Unknown | **0** |

An SPU program gives less than the PPU program: no descriptors, no unwinding tables, just a statically linked `.text`. So:

- **Calls and returns** are `brsl` and `bi $0`. Function pointers are addresses loaded by `ila` or held in data; both are taken as starts on weak evidence, and one that turns out not to be a function (it reaches a word that isn't an instruction) is dropped. One was: the sound core's jump table, whose address the code loads.
- **Nearly a third of the functions are called by nothing** (730 of 2,332). The linker kept every function of every object it took, so each program carries library functions it never uses (inline vector-maths functions emitted out of line, most likely). They are real code at clean boundaries (after a return or a jump, and the alignment padding), found one at a time, lowest first, so that a function's own later blocks aren't mistaken for functions. *Whether to lift them is the lifter's choice: nothing reaches them.*
- **One switch in all of the SPU code**, in the sound core: `bi` through a register, its four absolute addresses in the code at the next 16-byte boundary.
- `stop` with signal type 0 ends the start-up code (after `exit`, which doesn't return); the other 51 stops are services the program resumes after.
- 281 functions reach the next function's start without a return or a jump: they end in a call that doesn't return, or run into the function that follows (a tail call by falling through).
- `.SpuGUID`, 16 bytes marked executable before each program's code, is an identifier, not code. (v0.6.0 counted it: its figure of 209,660 words was 42 × 4 too many.)

**The channels** the programs use, which is the whole of what the runtime must provide in an SPU's place besides memory:

| Channel | Uses | What (by the published channel map) |
|---|---|---|
| write 16–21 | 780 each | a memory transfer: local address, effective address (high and low), size, tag, and the command that starts it |
| write 22, 23; read 24 | 370 each | wait for transfers: the tag mask, the kind of wait, the status |
| read 27 | 470 | atomic-command status (`getllar`, `putllc`: the lock-free primitives SPURS is built from) |
| write 28, read 29 | 85, 7 | the outbound and inbound mailboxes |
| write 30 | 42 | the outbound interrupt mailbox (once in each program: how an SPU calls the system) |

## The PPU lifter (`recomp/src/lift.*`, `runtime/include/qilin/rt/cpu.hpp`)

One guest function becomes one C++ function, `void fn_<address>(Cpu& c)`, in the shape the other Qilin recompilers use. `qilin lift <game>` lifts every function the control-flow pass found and says how many the lifter covers.

**Slice 1 (v0.8.0): 11,873 of the game's 14,294 functions lift, 641,755 of 1,059,387 instructions.** What stops the rest is the first instruction outside the slice: floating point (2,053 functions), VMX (363), the time base (5).

How lifted code is shaped:

- **Registers live in host locals.** A function reads the registers it uses from the `Cpu` on entry, works on locals (`uint64_t r3`, a four-bit `cr7`, `lr`, `ctr`, XER's bits one each), and writes them back only where another function can see them: before a call, a return, a trap, a system call; and reads them again after a call. Only the locals that may have changed since the `Cpu` last held them are written back (2026-11-28, "Lifted code's speed", below); at a direct call, only those the callee may read or write, and only what it may write is read again (round 3, below).
- **64-bit mode.** Registers are 64 bits, record forms compare the 64-bit result with zero, carries are out of bit 0 of 64. Only the "word" instructions look at the low 32 (compares with `L` = 0, `mullw`, `divw`, `slw`, `srawi`, the `rlw` rotates, which repeat the rotated word in both halves before masking, as the architecture defines them).
- **Addresses are 32 bits.** Every effective address is truncated before use; an update form writes the whole 64-bit sum back to its base register.
- **Memory** is the guest's bytes at `mem + address`, in the guest's order: a load is a `memcpy` and a byte swap. The base is a local copy (`m`), taken once at the function's start.
- **Direct calls and tail calls are C++ calls** (`fn_00403F14(c)`; a branch out of the function is a call and a return). A return is `return`. `bl` sets `lr` first: the callee may save it.
- **Indirect calls and jumps** (`bctrl`, a `bctr` that isn't a switch, `blrl`) go through `hooks->call` with the code address, which the runtime finds in a dense index (`runtime/include/qilin/rt/dispatch.hpp`).
- **A switch** is a C++ `switch` on CTR's value, a case for each target address in the table the control-flow pass read; anything else traps.
- **System calls** (`sc`) go through `hooks->system_call`; traps through `hooks->trap`, which doesn't return.
- `sync`, `dcbt` and the other cache and ordering instructions need nothing on a host with real threads' memory semantics: *to be revisited with the threading model.*
- A function that reaches the next function's start without a return (it ends in a call that doesn't return) calls that function and returns.

**Where the architecture leaves a result undefined**, the runtime's helper states its choice (`cpu.hpp`): a divide by zero or of the most negative number by −1 gives 0; the upper half of a word divide is 0 and of `mulhw` the sign extension; `mfocrf` gives the named field and zeros elsewhere. *These are choices, not measurements of the PPU. No code that depends on one is expected; if any is found, RPCS3 running the game is the reference.*

**Not in the slice, and not skipped silently:** a function with any instruction outside the slice is not lifted, and `qilin lift` counts it under the reason. After floating point (below) comes VMX; then `dcbz` and atomic sequences (which this game doesn't use). **Landing pads** were labels nothing could enter until after v0.13.1: "C++ exceptions", below.

With `--out <folder>` the lifted code is written out, 256 functions to a file (derived from the game: keep it out of the repository). All 11,873 functions compile with Visual Studio 2022 (checked on the owner's PC: 47 files, under three minutes).

### Slice 2 (v0.9.0): floating point, bit-exact

**13,732 of 14,294 functions now lift, 914,967 of 1,059,387 instructions.** What is left: VMX (560 functions) and the two functions that write and read the FPSCR.

The floating-point helpers are `runtime/include/qilin/rt/fp.hpp`. A register holds a double; the host's arithmetic is used where it is exactly the guest's, and corrected where it isn't (this is the exact mode, which the differential test runs; the game plays in the relaxed one since round 3: "Relaxed floating point", below):

- **NaNs.** PowerPC's result for a NaN operand is the first NaN operand in the order frA, frB, frC, made quiet, and for an invalid operation the positive default NaN. Hosts differ from that and from each other (x86's default NaN is negative), so every operation tests its result and works a NaN out itself.
- **Single-precision arithmetic rounds once.** `fadds` and its kin round the exact result of their double operands to single. With operands that are themselves singles (nearly always), the host's float arithmetic is that. With others, rounding the double result again would round twice: the slow path finds on which side of the double result the exact one lies (by error-free transformations: two-sum, the fused remainder of a product, quotient or root) and rounds through "round to odd", which makes the second rounding harmless.
- **The fused forms** (`fmadds`, `fmsubs` and their negatives) with frA and frC singles take the product exactly in a double and round one sum once. The host's single-precision `fma` is not used. Double-precision `fmadd` is `std::fma`.
- **Loads and stores of singles** convert formats as the architecture's own conversions do: no rounding, no quieting (a signalling NaN goes through `lfs` and `stfs` unchanged), a register that doesn't hold a single stored by bit selection.
- **Moves** (`fmr`, `fneg`, `fabs`, `fnabs`) are bit operations.
- Conversions to integer saturate, and give the most negative integer for a NaN. `fsel` and the compares are as defined; the compares set a CR field and nothing in the FPSCR.
- **The time base** (`mftb`) is a hook: the runtime will say what time it is.

**Assumed, and said where:** the rounding mode is round to nearest (the mode a program starts in), and the FPSCR's exception and result flags are not kept. So the instructions that read or write the FPSCR, and floating-point record forms, are not in the slice: a function that could notice is not lifted. The two that do (one `mtfsf`, one `mffs`, in the C library's environment functions by the look of them) are the two left. The estimates (`fres`, `frsqrte`), which the game doesn't use, are out too: their results are the hardware's tables'. The upper half of `fctiwz`'s result, undefined by the architecture, is `0xFFF80000`; `frsp` of a NaN keeps what of its payload a single holds; an arithmetic instruction passes a NaN's whole payload through. *Choices, to be confirmed against RPCS3 if anything is found to depend on them.*

**Its check is integers only.** The reference's floating point (`recomp/tests/difftest/ref_fp.cpp`) uses no host floating-point operation at all: a number is a sign, an integer significand and a power of two; sums, products, quotients and square roots are formed exactly in 128 bits (with a "sticky" note of anything below) and rounded once by one routine. So it shares neither a mistake nor a C library with `fp.hpp`.

- Floating-point arithmetic cases run from 1,200 states each (the hard cases are rare), drawn from the special values, singles, doubles exactly halfway between two singles and one unit either side, operands that nearly cancel, and noise.
- **4,765 cases, 1,085,808 runs, all agree.**
- It found one fault on its first run, in the slow path: a product that underflows in double lost its error term, and a tie was rounded the wrong way. Fixed, with the same hazard in the division path.

### Slice 3 (v0.10.0): VMX

**14,196 of 14,294 functions now lift, 1,016,630 of 1,059,387 instructions (96%).** What is left: 96 functions that use the two VMX estimates, and the two FPSCR functions.

The game uses a narrow part of VMX, and the slice is that part: `lvx`, `stvx`, `lvsl`, `lvsr`; the logical operations, `vsel`, `vperm`, `vsldoi`, the word merges and splats; `vadduwm`, `vcmpequw`; and single-precision `vaddfp`, `vsubfp`, `vmaddfp`, `vnmsubfp`, `vmaxfp`, `vminfp`, `vcmpeqfp`, `vcfsx`, `vctsxs`. Any other VMX instruction is outside the slice, by name.

The helpers are `runtime/include/qilin/rt/vmx.hpp`. A vector register is four words, element 0 first, each a host integer; bytes are numbered as the guest numbers them. All of it is portable C++ on fixed-size arrays (no host intrinsics, by the portability rule; since round 3 the relaxed mode's floating point is SSE and NEON beside a portable twin, as the roadmap now allows).

- Floating point is element by element and bit-exact by the same means as the scalar code: a NaN operand gives the first NaN operand made quiet, an invalid operation the default NaN; `vmaddfp` and `vnmsubfp` are fused, with the product taken exactly in a double and one sum rounded once.
- A recording compare sets CR6: "all true" and "none true".
- `lvx` and `stvx` drop the low four bits of the address.

**Assumed: non-Java mode.** VMX has a mode bit (VSCR's NJ) under which a denormal operand is taken as zero and a denormal result becomes zero. The game never touches the VSCR, so it runs in whatever mode its threads start in, and public descriptions say an LV2 thread starts with NJ set. `vmx.hpp` implements that, behind one switch (`kNonJava`). ***To be confirmed against RPCS3.*** The order of operands in the choice of a NaN for the three-operand forms (vA, vB, vC) is taken from the scalar rule: *likewise to be confirmed.* The VSCR's saturation bit is not kept, and `mfvscr` and `mtvscr` are outside the slice.

**`vrefp` and `vrsqrtefp` (v0.13.0; 170 uses in 96 functions) are estimates, and a stated choice.** The architecture asks only that they be within one part in 4,096 of 1/x and 1/sqrt(x); what a PPU gives exactly comes from tables of its own, for which this project has no source it may use. They were left unlifted until the game reached one (its first, at `0xdcaa0`, comes before SPURS starts). The choice made then: **the correctly rounded value**. It is within the architecture's bound, it is one definite thing a reference can check, and it says plainly what it is, where a table made up to look like the hardware's would not. It can differ from a console's result in the low bits. 1/x is a double's quotient, which rounds to the single correctly (a double has more than twice a single's digits and two); 1/sqrt(x) is the double's value settled exactly against the two midpoints beside it, by whole-number arithmetic (`compare_square`). The reference finds both by whole numbers alone: a division, and a search for the largest n with n·n·m ≤ 2^74. ***Still open:*** *the PPU's own tables, which would replace this if they can be had.*

The reference (`ref_vmx.cpp`) works on sixteen bytes in the guest's order, with arithmetic by the integer soft-float. Vector cases run from 400 states each. **5,403 cases, 1,327,632 runs in all, all agree**; a fault put into `vmaxfp` on purpose gave 426 disagreements. With the estimates (v0.13.0): **5,450 cases, 1,346,784 runs, all agree**; a wrong last bit put into each estimate on purpose gave 16,446 and 29,284 disagreements. **14,292 of 14,294 functions now lift, 1,059,366 of 1,059,387 instructions**: what is left is the two FPSCR functions.

### C++ exceptions: landing pads as entries (after v0.13.1)

The game's unwinder is lifted with the rest and walks the guest's frames by the program's own tables, in guest memory, so it works unchanged until its last step: once it has found a landing pad, it "returns" into it. **The shape, read off the program:** the program has exactly four instructions that move the stack pointer by a register, all `add r1,r1,r10` straight before a `blr`, at `0x418c68`, `0x418f9c`, `0x419210` and `0x419414`: `__builtin_eh_return`'s epilogue, at the end of each of the unwinder's four entry functions (libgcc's, by their shape). Before it the function reloads r14-r31, f14-f31, CR2-CR4, r2 and r3-r6 (the exception's data registers) from its own save slots, into which the unwinder has copied the landing pad's frame's registers, and LR from the slot where it wrote the pad's address; r10 is how far up the stack the pad's frame is, and 0 on the path that returns normally (set so just before). A lifted `blr` is a C++ `return` and can't go into the middle of a function further up, so:

- **The epilogue becomes a throw.** The lifter lifts `add r1,r1,rX` followed by an unconditional `blr` as the add, then, when rX isn't 0, every register written back to the `Cpu` and `eh_return(c)`, which throws `GuestUnwind{pad: LR, sp: r1}` (`cpu.hpp`). **The shape is confirmed, not guessed:** a stack pointer moved by a register in any other shape (the add not straight before an unconditional return, a record form) stops the function being lifted, by name; and `qilin lift` stops if the program has landing pads but no such epilogue. On the game: 4 epilogues in 4 functions.
- **A function with landing pads is lifted twice**: `fn_X_start(c)`, the function as any other, and `fn_X_pad(c, pad)`, which reads the registers from the `Cpu` (the guest's state at the throw: every function on the way wrote its registers back before its call) and goes to the pad through a `switch` at its top, so that what only the start reaches is dead code the compiler drops. `fn_X` hands both to `run_with_landing_pads` (`runtime/src/unwind.cpp`), the one `try` lifted code runs in: it runs the start; when a `GuestUnwind` arrives whose pad is one of the function's and whose frame is this activation's, it runs the pad's body, again for each later exception, and lets anything else pass on up the host's stack. The host's unwinding of the frames in between is what the guest's unwinder did to theirs. **Which activation:** a function makes its frame below the stack pointer it was entered with, and the frame's first word (the back chain `stdu r1` writes) is that stack pointer; so the frame at the exception's stack pointer is this activation's when its back chain is the stack pointer this activation was entered with. A recursive call of the same function, whose frame's back chain is another, lets the exception pass to the activation it is for.
- **Functions without landing pads pay nothing**: they are lifted as before. On the game, **932 functions with 2,845 landing pads** are lifted this way. A `GuestUnwind` no function takes reaches the runtime's `call_guest` (or the entry point's call), which stops the game by name with the pad and the frame.

**What it costs to compile** (MSVC 19.44, Release, `/w /bigobj`, one file at a time; before: the same files with the pads unreachable, as they were): the file with the most such functions (`lifted_020`, 129 of its 256) went from 20.3 s and 708 MB to 32.8 s and 874 MB (the pads' code, compiled away before, is compiled now); a typical one (`lifted_022`, 15) from 13.4 s and 599 MB to 14.2 s and 613 MB. The lifted text grows 28% (91.5 to 117.4 MB), most of it the start's code repeated in the pads' bodies, where it is dead and dropped early. Two other shapes were measured on `lifted_020` and rejected: a `try` in each lifted function, with the switch at the top of its one body (41.8 s, 1,557 MB), and the runtime's `try` with one body entered at its start or a pad (41.4 s, 1,170 MB): a body with several ways in compiles far worse than two with one each.

**Checked** by the differential test's unwinding program (below), whose reference knows nothing about exceptions, and by unit tests of the shapes the lifter takes and refuses. *Not yet seen in the game:* the game hasn't been run with it (the first exception it throws will show it).

### Lifted code's speed (2026-11-28)

The game's main thread runs guest code for milliseconds between system calls, so the lifted code's own speed is on the critical path. Measured first (a lift of the game into a scratch folder; MSVC 19.44 `/O2`; a microbenchmark of real lifted functions on synthetic guest memory, never committed), then changed where the measurement said:

- **Write-back of what changed only.** A forward dataflow over each function's instructions (`lift.cpp`, `flow`) finds, at each sync site, the locals that may differ from the `Cpu`: assigned on some path since the function's start, the last call (after which everything is read again) or the last write-back. Only those are written back; the rest the `Cpu` holds already. This is exact, not an assumption about the callee: the calling convention is still the full state (roadmap, "Calling conventions"). A conditional call (`bcl`, `bctrl` under a condition, `mtfsf`'s hook) leaves the set as it was; an unconditional one empties it. What a piece of text assigns is read off the text itself (`x = `, `x -= `, the carry's out-parameter), so the analysis can't drift from the emission.
- **Compare and branch folded.** A forward dataflow per CR bit carries the kind of every definition reaching it: a signed or an unsigned integer compare (record forms are signed compares with 0), a floating-point compare, a CR logical operation, or anything else (`mtcrf`, `mcrf`, a call, a VMX compare: opaque). Where all the definitions reaching a branch's bit are of one kind, the compares keep their operands in locals (`k7a`, `k7b`; `k7x`, `k7y`; `kb30` for a CR logical operation's bit) and the branch reads them: `if (k7a == k7b)`, which compiles to one compare and jump. Before, every compare built the 4-bit field (a compare, a branch, a `cmov`, an OR with SO, which the compiler can't see is 0 or 1) and the branch tested a bit of it. The field is still set, for the reads that don't fold and the write-backs; it's dead, and dropped, where nothing reads it. An integer compare's SO bit is never folded. The fallback is the field's local.
- **Memory through a local base.** A store through a byte pointer may alias anything, so with `c.mem + address` the compiler read `c.mem` again after every store; now `uint8_t* const m = c.mem` is read once. A load is then one `mov` and a `bswap` (MSVC folds a load swapped and stored swapped back into a plain copy).
- **The VMX fused forms.** `vmaddfp` and `vnmsubfp` were 22 ns each with MSVC (four elements, each with its NaN, denormal and two-sum checks). A whole-vector fast path takes four plain elements (normal or zero: no NaN, infinity or denormal), forms each sum from the exact product in a double, and rounds it to single directly, unless the double is exactly halfway between two singles or outside the singles' normal range (`fp::rounds_once_to_single`): no halfway point of singles can lie between the true sum and the double nearest it, so rounding the double once more gives the same single, except when the double is itself such a point. Anything else goes, out of line, to the general path. The scalar `fmadds` family's `add_to_single` takes the same test before its two-sum. `vperm` (a table of the 32 bytes) and `vsldoi` (whole words, and the bytes between two) no longer move one byte at a time. `vaddfp` stays element by element: a whole-vector form measured slower with MSVC.
- **Measured and rejected:** a compare without branches, `2 << ((a < b) << 1 | (a > b))`: MSVC 19.44 miscompiled it in one of the differential test's programs (CR0 came out "equal" for a negative product; the plain form passes). Reading back after a call only the locals live after it (a backward liveness pass, write-backs counted as uses): it cut the text by 18%, but MSVC then took 16 s over one 7,400-line function with 460 calls (`lifted_022`, 1.9 s with every local read back; the whole file 20 s instead of 6): the reloads that the compiler drops itself are what keep its live ranges short.
- **Not done, by the brief's rule:** writing back at a call only what the callee reads (the ELFv1 convention, or an analysis of every callee). Proving it needs the whole program's call graph, where any indirect call, system call or throw reads everything; it is left for later, and is item 1 of `docs/efficiency-research.md`. (Done in round 3, below.)

| | before | after |
|---|---|---|
| lifted text (without / with `--pc`) | 117.4 / 129.0 MB | 108.2 / 119.9 MB |
| `lifted_022` (MSVC, one file) | 13.4 s, 615 MB, 2.76 MB object | 6.1 s, 400 MB, 1.77 MB |
| `lifted_022` with `--pc` | 14.5 s, 621 MB | 6.5 s, 392 MB |

The microbenchmark (MSVC, ns a call, best of seven rounds of 20,000; each run's registers and memory hashed, and the same old and new): `memcpy` of 256 bytes 42.6 to 39.5 (with `--pc` 56.3 to 43.9), of 13 bytes 32.2 to 29.2; `memset` of 256 bytes 33.1 to 29.4; `strlen`, `memcmp` and two floating-point functions unchanged within 2%; `memchr` of 63 bytes 57.5 to 69.1 (*a loss not yet understood*: the loop is a CTR decrement, a byte load and a folded compare); the two largest VMX leaf functions (128 and 124 `vmaddfp`) 2,887 to 2,260 and 2,008 to 962; a function making 14 calls (to empty stubs) 31.1 to 30.5. ### Calls narrowed, fields formed late, floating point relaxed (2026-11-28, round 3)

Measured the same way (a scratch lift of the game, the microbenchmark of real lifted functions on synthetic memory, MSVC 19.44 `/O2` on a Ryzen 7 5800X, ns a call, best of seven rounds of 20,000, never committed).

**The `memchr` loss, found.** Its loop (a CTR decrement, a byte load, a compare and branch) built CR7's four bits on every pass (a compare, a branch, a `cmov`, an OR with SO) for the one write-back at the loop's exit; and MSVC put the loop's 44 bytes across a 64-byte line in one build and not in another, which alone moved it between 69 and 60 ns with the same code (the 57.5 before was such a placement too). The first is the lifter's to fix:

- **Lazy condition fields.** A field whose every bit read folds, whose local nothing reads by name (`mfcr`, `mcrf`, a CR logical operation reading its own field), and which only compares assign, isn't set at the compares at all: they keep their operands, and each write-back forms the field from them (`compare_s(k7a, k7b, so)`, `compare_u`, `fp::fcompare(k7x, k7y)`). Where the field as the `Cpu` held it (at the start, after a call) or compares of different kinds reach the same write-back, a small local says which (`kf7`: 0 the field's local, else the last compare's kind); it is a constant on each path, so the compiler folds it into the edges and the loop carries nothing (`(kf7 == 1u ? compare_s(...) : cr7)` at the exit). An integer compare's SO bit is the `so` local at the write-back: a function that sets SO itself (`mtxer`) keeps its integer compares' fields eager. `memchr` of 63 bytes 69.1 to 35.7, `strlen` 45.6 to 33.2, `memset` 29.5 to 27.2; the rest within 2%; every state hash the same.

**Calls narrowed by what the callee reads and writes** (item 1 of `docs/efficiency-research.md`). `register_effects` (`lift.cpp`) computes, for every lifted function, the registers it may read before writing them and those it may write (as the lifter's 109 locals), from its own lifted text read as the dataflow reads it (`assigned`, `used`: placeholders included, so a compare's operands are reads of their registers and a folded bit read is a read of its field) and its callees' effects, to a least fixed point over the program's calls (a worklist over each function's callers). A function's writes are all it assigns and all its callees may write; its reads come from a backward pass from its returns in which each piece of text reads what it uses after killing what it assigns, and each call reads what its callee may read (a callee's writes may not happen, so they kill nothing). Anything that may call through a register, call the system or a hook (`mtfsf`'s), throw (`__builtin_eh_return`'s epilogue), or that has landing pads (whose body reads everything from the `Cpu`), or that calls or runs into a function not lifted, reads and writes everything. A trap adds nothing: it doesn't come back, so what it would read is nobody's (*its report can then show a caller's register as it was before the caller's last change; `--registers` turns the narrowing off*). A function whose declared locals its text wasn't seen to read or write is taken to read and write everything, so a reading that misses something fails safe.

- At a direct call the caller writes back what may have changed **and the callee may read or write**: what it may write, and on some path doesn't, must be in the `Cpu` already, since the caller reads it again after the call (writing back only what the callee reads is wrong for that reason: broken that way on purpose, 535 disagreements). It reads again only what the callee may write; with SO, every CR field too (a lazy field takes SO from its local). What the callee neither reads nor writes stays in the caller's locals, still to be written back at a later sync, and a fold on a CR field the callee doesn't write survives the call.
- **On the game:** 12,035 of the 14,294 functions read and write less than everything; 25,833 of the 60,340 direct calls and tail calls are narrowed. The lifted text 108.4 to 99.7 MB. `qilin lift` takes 5.6 s with it. Compile time (MSVC, one file at a time): `lifted_022` 6.3 s, 406 MB, 1.73 MB object to 5.2 s, 333 MB, 1.11 MB; `lifted_020` (129 functions with landing pads, which read everything) 23.4 to 23.1 s; the 7,400-line function with 460 calls (`fn_001C3818`) alone 3.1 s, 214 MB, 1.20 MB to 2.0 s, 129 MB, 615 KB. (Narrowing the reloads by liveness, which the round before measured at 16 s for that function, isn't what this does: the reloads left are what the callee may write, and the compiler still sees each one.)
- The microbenchmark's functions are leaves or call stubs, so it barely moves: the 14-call function 30.0 to 29.8.

**Relaxed floating point** (item 8; the owner's decision of 2026-11-28). `QILIN_FP_EXACT` (a build-time macro, the same for the lifted code and the runtime) picks the mode: **relaxed (0) is the default, the game's build; the differential test defines 1** (in `cases.hpp`, which stops a test file that includes `cpu.hpp` before it in the other mode). Both modes are always defined (`fp::exact` and `fp::relaxed`, `vmx::exact` and `vmx::relaxed`, `vmx::portable`), and the mode is a `using namespace` that decides which one `fp::fadds` and the rest name; so a test can call both, and the two can't break the one-definition rule.

- *Scalar:* the host's double arithmetic and `std::fma`; the single operations in double, then rounded to single (`static_cast<float>(a + b)`); the single fused forms the double sum of the exact product, rounded to single; `frsp`, `lfs` and `stfs` plain conversions. No `is_single` tests, no slow paths, no NaN checks.
- *VMX:* SSE on x86-64 (`_mm_add_ps`, `_mm_max_ps`, `_mm_cmpeq_ps`; `vmaddfp`/`vnmsubfp` in doubles two elements at a time, or `_mm_fmadd_ps` where the build has FMA; `vrefp` and `vrsqrtefp` as `_mm_div_ps` and `_mm_sqrt_ps`; `vctsxs` as `cvttps2dq` with the top end and NaNs put right), NEON on ARM64 (`vfmaq_f32`, the guest's own one rounding; `vmaxfp` as a compare and select, so it agrees with SSE's choice; `vcvtq_s32_f32`, which saturates as the guest does), and a portable twin (`vmx::portable`, used elsewhere and with `QILIN_VMX_PORTABLE`) that gives the same results.
- *Denormals:* `fp::enter_thread_mode` sets the host's flush-to-zero for operands and results (x86's DAZ and FTZ, ARM's FZ) once per thread, from the runtime's `run_lifted` before it runs lifted code: what VMX's non-Java mode asks; scalar arithmetic on denormals, which the guest keeps, then gives zero. In exact mode it does nothing.
- *Both modes:* `fctiw`, `fctiwz`, `fctid` and `fctidz` are now inline and exact without a library call (`std::nearbyint` and `std::trunc` were calls with MSVC, and the saturation was out of line): a compare for the range, a cast, and for rounding to nearest |b| + 2^52 - 2^52 with the sign put back.
- **Where relaxed differs** (the differential test's `run_relaxed` checks each bound on ordinary values, normal singles of exponent 64 to 190, and doubles of them): NaNs (the host's default NaN, negative on x86, and its choice among NaN operands; a signalling NaN loaded by `lfs` made quiet); denormals (above); zeros of both signs in `vmaxfp`/`vminfp` (the second operand, as SSE gives); `stfs` of a register that doesn't hold a single (rounded, where the guest selects bits). On ordinary values: the single and double arithmetic on singles, `lfs`, `stfs`, `vaddfp`, `vsubfp`, `vmaxfp`, `vminfp`, `vcmpeqfp` and `vrefp` are **bit-equal** to the exact mode (a double holds more than twice a single's digits plus two, so rounding a double result again to single is harmless: 200,000 operand sets, none differ); `vctsxs` is bit-equal on any bits at all; the single fused forms are **within one unit** in the single's last place, equal except where the double sum lands on a point halfway between two singles (40,000 built so differ by exactly one; none of 1,200,000 ordinary ones); single operations on doubles that aren't singles round twice, within one unit (none of 800,000 differed); `vrsqrtefp` rounds twice (the root, then the quotient), within two units (one seen, in 70% of vectors). Broken on purpose (`fadds` off by a part in 2^26, `vmaxfp`'s operands swapped): 110,989 disagreements.
- *Contraction:* `-ffp-contract=off` stays for everything (CMake's, and it keeps the exact mode honest). Measured for the relaxed mode with Clang 19 built for x86-64-v3 (where there is an FMA to contract to): `-ffp-contract=fast` gave the `fmadds` function 31.1 to 29.8 ns and the wrap loop 8.3 to 7.8, the VMX functions the same, the states the same. The guest's fused instructions are fused already (`std::fma`, `vfmaq_f32`, `_mm_fmadd_ps`); contracting the rest would fuse what the guest rounds twice, for under 5%. Not taken. (MSVC doesn't contract by default, and x86-64 without `-mfma` has nothing to contract to.)
- **Measured** (old: before this round; exact and relaxed: after, with the lazy fields and the narrowed calls): `fmadds` x20 97.2 / 94.7 / 49.1; the two VMX leaves 2,237 / 2,211 / 610 and 972 / 963 / 318; the wrap loop 22.5 / 22.5 / 23.0. The integer functions come out up to 2 ns slower in the relaxed build than in the exact one: the same binary with and without the flush-to-zero mode times the same, so that is where the linker put them. With Clang 19 (baseline x86-64, the same lift), exact against relaxed: `fmadds` 88.2 to 34.0, the VMX leaves 2,104 to 343 and 813 to 166, the wrap loop 12.9 to 9.6; with x86-64-v3 (FMA) the VMX leaves 134 and 97.

### The differential test (`recomp/tests/difftest/`, `qilin_difftest`)

The lifter is checked against a **reference interpreter written separately** (`ref.cpp`): from the architecture's definitions, on the raw word's fields, with CR and XER as packed words, carries taken bit by bit, masks built bit by bit, products by long multiplication, memory a byte at a time. It shares only the decoder's naming of the opcode with the lifter. It runs in tests only: nothing interprets at run time.

- `qilin_difftest_gen` (at build time) lifts 24 random valid encodings of each instruction in the slice as a one-instruction function, and small programs for what a single instruction can't show: every conditional branch form the decoder accepts over a spread of condition bits, `bclr`, `bcctr`, traps, a call, a tail call, a system call, a switch.
- `qilin_difftest` (in `ctest`, so in CI on all six configurations) runs each from 48 random states, weighted towards the edges (zeros, ones, the sign boundaries of each width, a counter about to reach zero), with loads and stores steered into a window of memory and noise above bit 31 of the address. Registers, CR, XER, LR, CTR, the memory, and whether and where it trapped, jumped or called the system must all agree.
- Slice 1 alone: 3,602 cases, 172,896 runs, all agree, 135 instructions covered one at a time. With the later slices: **5,403 cases, 1,327,632 runs, 210 instructions.**
- That the test can fail was checked by breaking a helper on purpose (the carry of `sraw`): 179 disagreements, named.
- **The unwinding program** (after v0.13.1): three functions of a program `elf_builder` makes, with its `.eh_frame` and an exception table, found by the control-flow pass and lifted as the game's are. A calls itself to a depth of 0 to 2, then B, which calls U; U stands in for the unwinder and ends in `__builtin_eh_return`'s epilogue, returning normally, or sending the exception to the outermost or the innermost A's frame, or to a frame on no one's stack (which must come out of the outermost A). The reference runs the program instruction by instruction, the epilogue being just an add and a return to LR, so it lands at the pad knowing nothing of exceptions; registers, CR, LR, CTR and the stack must agree, and a count kept in r7 says which frames finished. 96 runs, all agree; with the frame check taken out of `run_with_landing_pads` on purpose, 120 disagreements, and with the throw never made, 360. (`add r1,r1,rX` is left out of the one-instruction cases: before a return it is the epilogue.)

- **Programs** (2026-11-28, for the dataflow): 400 random functions of 14 to 60 instructions: integer operations, compares into any field (some with a branch on that field a few instructions later, past a call sometimes), record forms, CR logical operations, `mfcr`, `mtcrf`, carries, loads and stores off r1, forward branches on any CR bit and on CTR, and calls, some conditional, to a helper that changes registers, CR fields and the carry, or nothing; every third lifted with `--registers`. The reference interprets the words. 19,200 runs, all agree. Broken on purpose: a conditional call taken to empty the set of changed locals gave 13,231 disagreements; the fold's join ignoring a second, different definition 2,482. (The programs also found the miscompiled compare above.) `qilin_tests` checks the shapes: a branch on a field set two blocks earlier reads the compare, one after a call reads the field, mixed kinds don't fold, `fcmpu` and `cror` fold, `mfcr` reads every field, a call writes back only what changed.
- **Rounding once to single** (2026-11-28): 400,000 operand triples, half built so that the product sits about half a unit of the addend's last place away from it (so the double sum lands on or a hair off a halfway point between singles): `fmadds`/`fmsubs` against the reference's integer soft-float, `vmaddfp`/`vnmsubfp` against their general path. With the halfway test taken out, 212 disagreements.
- **Programs of three functions** (round 3, for the narrowed calls): 300 of them, main calling mid and leaf, mid calling leaf, each call plain or conditional; leaf's and mid's random instructions use a few registers of their own, so each call syncs part of the state; compares and branches on them before and after the calls, loads and stores, carries. All the programs (these and the 400 above) are lifted with their functions' effects: 1,242 calls narrowed. 33,600 runs of programs, all agree; written back only what the callee reads, 535 disagreements. `qilin_tests` checks the effects of a few functions (a leaf, a caller of it, a system call, a call to a function not lifted) and a narrowed call's shape.
- **Relaxed floating point** (round 3, `run_relaxed`): the bounds above, the vector code against its portable twin, and the flush of denormals on a thread of its own.

## The SPU lifter (`recomp/src/spu_lift.*`, `runtime/include/qilin/rt/spu.hpp`)

Started after v0.13.0, when the game reached the first thing that needs an SPU program running (its sound core, started as an SPU thread).

**The shape** is the PPU lifter's, and simpler: an SPU has no condition register and no table of contents. A lifted function is `void fn_XXXXX(Spu& s)`; each instruction is one call of a helper in `spu.hpp`, written from the SPU's published instruction set (forced inline, and most of them a vector instruction or two). Each of the 42 programs is lifted into a file and a namespace of its own (`spu_p00` to `spu_p41`: they all sit at the same addresses), with a `call(s, target, pc)` that is a switch over the program's function starts, for branches through a register. `qilin lift <game> --out` writes them beside the PPU's files, with a table (`kLiftedSpuPrograms`: where each program's ELF lies in the PPU program's memory, which is how the game names it to the system; its entry point; its `call`).

- A register is four words, the preferred slot first, and also the host's 128-bit vector (`SpuReg` is a union of the two: x86-64's `__m128i`, ARM64's `uint32x4_t`). The local store is 256 KiB **in the host's word order**: each aligned word is a host `uint32_t`, so a quadword's load or store is one 16-byte copy into a register's words (before, four byte swaps each way). SPU byte `a` is host byte `a ^ 3` on a little-endian host; whatever moves bytes between the local store and the SPU's byte order (memory transfers, a program's loading, `sys_spu_thread_read_ls`/`write_ls`, the SPURS kernel's data) goes through `spu::ls_read`/`ls_write`/`ls_word`. A quadword's address is masked into it at a multiple of 16, as the SPU does.
- **The registers a function uses are locals** (`SpuReg r3 = s.r[3];`), as the PPU's are: those it writes go back to the `Spu` before every call, tail call and return, and all it uses are read again after every call (the callee may change any). Within a function they live in the host's vector registers. Only `native_call` (reached through `call`) sees the registers; the channel, stop and halt hooks must not look at them. Before (registers in the `Spu`, read and written by every instruction through `Spu&`), every instruction went through memory, and no compiler could keep a value in a register across a local-store write (a `uint8_t` store may alias anything).
- Within a block (to the next label or call), a register set by `il`, `ilh`, `ilhu`, `ila` or `fsmbi` holds a known constant: an `iohl` after it is one constant (`ilhu`/`iohl` pairs make every 32-bit constant), and `fsmbi` is its constant. `ori rt,ra,0` and `shlqbyi rt,ra,0`, the compiler's moves, are copies. The immediate shifts and rotates (`shli`, `rotmi`, `rotmai`, the halfword forms) are their own helpers, one vector shift each.
- **The helpers** (`spu.hpp`) are SSE2 on x86-64 for the common instructions (adds, logic, compares, `selb`, the immediate shifts, sign extensions, loads and stores); `shufb` and the whole-register byte shifts and rotates are SSSE3 (`pshufb`, the byte shifts from a table of the 32 shuffles of each kind) where the build may use it (`QILIN_SPU_SSSE3`: MSVC always, GCC and Clang when built for it; the runtime stops at its first SPU thread, by name, on a processor without SSSE3, which every x86-64 processor the game could run on has). On ARM64 (little-endian, GCC or Clang) they are NEON (below). `fa`, `fs`, `fm`, the fused forms and the float compares are the host's float unit inline in the relaxed way, and out of line in the exact ways (`spu_fp.hpp`, below). Elsewhere and for the rarer instructions the helpers are plain C++ on the four words, which stay the reference. `QILIN_SPU_PORTABLE` builds the plain C++ on x86-64 too, for testing it.
- **The preferred word's own local** (after v0.13.1). Where a register's preferred word is read (an address, a branch's condition, a shift's count), the lifter gives it a `uint32_t` local beside the vector (`p3`), kept equal to the vector's word at every write, and read again after calls. Where it is cheaper to have from the operands' words than from the vector, it is: a sum or difference, a logical operation, a compare (`ceq`, `cgt`, `clgt` and their immediate forms), a shift left by an immediate, a copy, a constant; and **a pointer followed**, `lqd x, k(b)` then `rotqby y, x, b` with nothing stored or called between, which is the word at `b + k` (`spu::word_at`: one load when it is a word's, the shuffle when not). An address or a branch then waits for scalar arithmetic and one load, not for the vector unit and a move out of it. The lifter finds which registers get one in passes: first all whose word is read and those such words are made from, then only those that some instruction gives a word other than the vector's or a constant (the others would cost a copy at every write for nothing). The differential test's programs now follow a pointer twice and branch on what they found.
- Calls are `brsl` (the callee is called; `$0` gets the return address, as the program expects to find it), returns `bi $0`. `biz`, `binz` and the halfword forms through `$0` are conditional returns. A branch to another function's start is a tail call. A function that reaches its end without a return runs into the next one (281 do). The one switch is a `switch` over its table's targets.
- Channels and `stop` go to hooks (`SpuHooks`), which the runtime provides; a halt instruction that fires, or a branch to an address that is no function, is the hook `halt`, which doesn't return.
- Outside the slice, by name: floating point (the next slice), interrupts (`iret`, `bisled`, and indirect branches that enable or disable them: the game has none), the special-purpose registers.

**Slice 1: everything but floating point. 1,719 of the 2,332 functions lift.** Every one of the other 613 is stopped by a floating-point instruction (`fm` in 225, `fcgt` in 143, `fs` in 101, ...): nothing else is in the way.

**The differential test** (`recomp/tests/spu_difftest`, `qilin_spu_difftest` in `ctest`) is the PPU test's twin: the generator lifts random encodings of every instruction in the slice that is not a branch (148 instructions, 3,552 cases), the runner runs each from 64 states (227,328 runs) as lifted code and by a separately written reference, and compares all 128 registers, the whole local store after a store, what was written to a channel, a stop's code and whether a halt fired. The reference (`ref.cpp`) is in another shape on purpose: a register is sixteen bytes, elements are read and written by width and number, and the whole-register shifts work on the register as one 128-bit number, where the helpers work on words and bytes. **All agree**; with `sumb`'s halves exchanged and `rotqmby`'s count cut short on purpose it gave 7,908 disagreements. **Programs** (after v0.13.1, with the registers in locals): the generator also makes 200 small random programs of two functions, built as an SPU ELF and taken through the control-flow pass and the lifter whole: the first loops one to three times over random instructions, a conditional branch over some of them, an `ilhu` before and after that branch completed by an `iohl` after its target (so a constant known on one way in only), and a call to the second, which returns early on a condition. The runner runs each from 64 random states against the reference stepping through the words (`run_program`: the relative branches, `brsl`, and `bi $0` and its conditional forms as returns) and compares everything as for single instructions: **all 12,800 runs agree**, and so do they with the plain C++ helpers (`QILIN_SPU_PORTABLE`) and with SSE2 alone (`QILIN_SPU_SSSE3=0`). With the registers not read again after a call it gave 64,220 disagreements, and with the constants known across a label 29,611. *The switch is still checked only by the game's own programs running.*

### Speed (after v0.13.1)

Measured outside the repository on the game's own lifted programs: a benchmark runs a SPURS task's program from its entry on a made-up machine (guest memory of pseudo-random words, a small memory-transfer engine, the SPURS kernel's data) to its end, old lift against new, and checks that both leave the same local store, registers and guest memory. With MSVC on the owner's PC: `SmokeCreateVertex_r.elf` 31.1 ms a run to 4.1 (7.6 times), `SmokeFrameMove_r.elf` 123 to 39 microseconds (3.2 times). The same helpers under the old lift (registers in the `Spu`) took the first to 7.3 ms: most of the gain is the vector helpers, the rest the locals. The heaviest file to compile, `spu_p24`, takes MSVC 15 s and 0.6 GB, from 169 s and 4.2 GB (its 2,500-line function no longer inlines scalar loops of sixteen bytes); the largest, `spu_p41`, 62 s and 1.1 GB from 85 s and 1.35 GB. What is left in those runs is the programs' own work: a pointer chase through a free list (`lqd`, `rotqby`, `lqd`), the transfers. The channels cost nothing worth having: under a thousand hook calls in a 31 ms run.

**After v0.13.1, round 3** (the same benchmark, MSVC, best of 30 or 300 runs; the machine shared with other builds, so a few percent either way is noise): `SmokeCreateVertex_r.elf` 4.10 ms a run to 2.43 in the exact way and 2.37 in the relaxed (1.7 times), nearly all of it the preferred word's local on its free-list walk; `SmokeFrameMove_r.elf` 32.2 microseconds to 32.6 in the exact way and 22.4 in the relaxed (1.4 times; its benchmark data has random words, which the exact way often sends down its whole-number path). The exact ways' results are the same bit for bit as before (the benchmark's hash of the local store, registers and guest memory). The largest lifted file, `spu_p41`, compiles in 35 s and 0.54 GB, from 55 s and 1.1 GB, and `spu_p24` in 13 s and 0.38 GB, from 20 s and 0.6 GB: the exact ways out of line.

**ARM64.** The same helpers in NEON: `shufb` is `tbx` of the two operands side by side with the constants from a second table by the control's top three bits (five instructions), the byte shifts and rotates `tbl` of the same table as SSSE3's, the element shifts the per-lane shifts (`ushl`/`sshl`, which give zero or the sign past the width as the SPU does; by an immediate, one `shl`/`sshr`, or `shl` and `usra` for a rotate), the multiplies `umull`/`smull` of the narrowed halves, `cntb` `cnt`, `sumb` two pairwise adds, `xswd` one `trn2`; the float unit with FPCR set to round toward zero and flush to zero (an `msr` as the thread starts), and its fused multiply-add, which rounds once as the SPU's does. **Verified:** cross-compiles with zig's Clang for `aarch64-linux-gnu -mcpu=cortex-a72` and `aarch64-macos` with `-Werror`, and the hot helpers' assembly read (as above). The differential test ran the NEON helpers on x86-64 through a header of NEON's intrinsics written lane by lane from ARM's descriptions (`QILIN_SPU_NEON_TEST`, the header outside the repository): all agree, and the relaxed way's fused forms are the same as the exact ones there. **Not verified:** a run on ARM64 hardware or an emulator (none was at hand), so the intrinsics' own meaning on a real processor, and whether FPCR's flush-to-zero applies to the float compares (ARM's documents say it does for the arithmetic) rests on reading, not running. *Owed: the differential test on a Pi.*

### Slice 2: floating point (`runtime/include/qilin/rt/spu_fp.hpp`)

**2,330 of the 2,332 functions now lift.** The two left read and write the floating-point status and control register (`fscrrd`, `fscrwr`: one program's library functions), which is not kept, as the PPU's is not.

**After v0.13.0: all 2,332 lift, and all 14,294 of the PPU's.** The status registers are kept as written, not as arithmetic would set their flags (*a stated choice*: the runtime rounds to nearest and raises nothing). On the PPU, `mffs` reads the FPSCR into a register's low word (the high word, undefined, is 0) and `mtfsf` writes the fields its mask picks, with FEX and VX as their summaries; the game uses them in the C library's `fegetenv` (`0x3fc55c`) and `fesetenv` (`0x3fc184`). If `mtfsf` leaves a rounding mode other than to nearest, non-IEEE mode or an exception enabled (the low byte not 0), lifted code calls `CpuHooks::fpscr_mode`, which stops the game by name. On the SPU, `fscrwr` keeps the bits the instruction set defines (20-23, the two double-precision slices' rounding modes, and the sticky flags) and `fscrrd` reads them; a rounding mode other than to nearest halts. The other FPSCR instructions (`mtfsfi`, `mtfsb0`/`1`, `mcrfs`) and the record forms stay out: the game doesn't use them. Both differential tests start every case from a random status register and compare it after (5,498 cases, 1,404,384 runs on the PPU; 4,128 cases, 374,784 runs on the SPU; all agree), and each fails when a bit of the summaries or the defined mask is broken on purpose.

The source is IBM's public *Synergistic Processor Unit Instruction Set Architecture* (version 1.2, January 2007), section 9, read from the Internet Archive's copy.

**Single precision is not IEEE's**, and is done in whole numbers, exactly:

- a word with a zero exponent is zero whatever its sign and fraction (no denormals); every other word is an ordinary number, the largest exponent included (no infinities, no NaNs);
- results are truncated toward zero, the only mode there is; a result too large becomes the largest number of its sign (`0x7FFFFFFF`, `0xFFFFFFFF`), one too small becomes zero, and a zero result is always +0;
- `fma`, `fms` and `fnms` multiply exactly and round once.

So a sum is aligned in 64 bits with what falls off remembered, a product is exact in 48 bits, and the result is cut once (`pack`). The compares take every zero-exponent word as the one zero. The conversions' scale is 155 or 173 less the instruction's field and is defined from 0 to 127: an instruction outside that is outside the slice.

**`fi` is defined exactly** by the document (a base `1.BBBBBBBBBBBBB`, a step `0.000SSSSSSSSSS`, and the operand's low 19 bits as the fraction between them) and is exact here. **The estimates' base and step are an implementation's own**: the document gives their form and how good the result must be after its Newton-Raphson step, not their values, and a console's are not known here. *The stated choice:* 32 straight pieces to the binade for 1/x, and 64 for 1/sqrt(x) (32 for each parity of the exponent), each the line through its piece's ends lowered by half its error at the middle, rounded to the 13 and 10 bits the form has. A result can differ from a console's in the low bits. ***Open:*** *a console's tables, which would replace this.*

**Three ways, one for the whole process** (after v0.13.1, the owner's decision of 2026-11-28: a fast, relaxed way for play, the exact way for tests):

- `whole`: everything in whole numbers, as above, whatever the float unit is set to. The differential test's, and the way before an SPU thread starts.
- `exact`: the host's float unit (round toward zero, denormals flushed in and out: MXCSR on x86-64, FPCR on ARM64), with zeros made +0 and the lanes it can't stand in for (an operand with exponent 255, a result of 2^127 or more) done again in whole numbers. The same results bit for bit as `whole`.
- `relaxed`, **the default for play**: the host's float unit as it is, only a zero result made +0 (two instructions). Within the ordinary range (normal numbers whose results stay below 2^128) the same bit for bit for an add, subtract, multiply and compare, and for ARM64's fused forms; x86-64 may lack a fused multiply-add, so its fused forms are a multiply and an add, each truncated, within two units of the last place of the larger of the product and the addend. Where it differs: an operand with exponent 255 is an infinity or a NaN to the host (to the SPU, a number of 2^128 or more), a result of 2^128 or more is `0x7F7FFFFF`, not the SPU's next binade or its saturation at `0x7FFFFFFF`, and a compare with such an operand is IEEE's. Conversions, estimates and double precision are exact in every way. This is the shape RPCS3 describes publicly for its "approximate xfloat" (no code of it read).

The way is a process-wide value set by `spu::enter_single_mode` (the runtime calls it as each SPU thread starts, which also sets that thread's float unit) and read once per instruction from a plain global, not the thread's own storage (a thread-local was three loads on Windows). `QILIN_SPU_FLOAT=whole|exact|relaxed` in the environment chooses it at run time, `QILIN_SPU_FLOAT_DEFAULT` (0, 1, 2) at build time. Each float instruction's inline form is the relaxed one; the exact ways are a call (`exact_single`, `exact_compare`: a test and a branch the processor predicts). The differential test runs every float case in both exact ways (half the runs each, the float unit set for `exact`), and checks the relaxed way apart (`check_relaxed`): 1,000,000 vectors of ordinary numbers, zeros and denormals, the add, subtract, multiply and compares the same bit for bit and the fused forms within their bound, and the differences above shown where they are said to be. *Known:* a compiler may fold a float operation on two constants with round-to-nearest at build time; the lifted code doesn't do that arithmetic on constants that we know of.

**Double precision** (three instructions and the two conversions, in three programs) is IEEE's on the host's doubles, with two choices the document leaves to the implementation, stated: a denormal operand is zero with its sign, and a NaN result is always the default one. Rounding is to nearest. The fused double forms and the double compares, which the game doesn't use, are outside the slice.

**Checked.** The differential test now has **4,080 cases and 362,496 runs, all agree**. The reference's floating point (`ref_fp.cpp`) uses another method on purpose: every number is put whole into one 704-bit unsigned number at its true place, sums and differences are exact, and only then is the answer cut to 24 bits; it builds the estimates' tables by whole numbers of 2^-40. Float cases draw their operands from singles of every kind (zeros, denormals, the ends of the range, the largest exponent, neighbours that cancel). With the sum's borrow left out on purpose: 24,068 disagreements. **The estimates are also checked against the document's own bound**: over 2,000,000 numbers, its two sequences (estimate, interpolate, one Newton-Raphson step) give the largest single below the true value or the one beside it, as it requires (the furthest is 1 unit for each); with the tables' lowering turned the wrong way on purpose, 1,839,906 of them break the bound.

## The RSX's programs (`recomp/src/rsx_program.*`)

The game's first frame draws, so its vertex and fragment programs have to be translated before anything is shown; the first piece is reading them. `qilin shaders <game>` decodes and checks all 242; `--disasm` prints each with its parameters.

**Sources.** The field layout is the NV40's, from the public description in the nouveau driver's documentation (Mesa's `nv40_vertprog.h` and `nvfx_shader.h`, MIT-licensed: read for the facts, no code taken), as `prior-art.md` names. The Cg binary's layout (the program header, the parameter table with types, resources, register indices, names, semantics and, for fragment programs, where each constant is patched into the microcode) is NVIDIA's, published with the Cg toolkit; it was confirmed field by field against the game's bytes before use.

**Vertex programs**: four words an instruction, a vector and a scalar operation in each, with separate destinations. **Fragment programs**: four words an instruction, each word stored with its 16-bit halves exchanged; one that reads a constant is followed by the constant, four more words.

**Where the RSX differs from nouveau's NV40 headers, as the game shows:**
- a vertex instruction's constant index is **10 bits** (word 1, bits 12-21), not 8: the game reads constant 467, and the Cg tables name it so;
- in fragment instructions, word 3's bits 19-29 (nouveau's input-address displacement) are `0x7FC` exactly when the instruction reads an input, and 0 otherwise; word 2's bits 19-21 are 5 on `NRM` and 0 everywhere else (*not understood*; held to that by the check);
- the RSX's own operations: `NRM`, `DIV`, `DIVSQ`, `FENCT`, `FENCB` (fragment), beside the NV40's.

**The check** (`check_program`) is this decoder's independent reference, as objdump is the CPU decoders': every program against its own Cg tables. **All 242 agree, over 7,702 instructions:** every set bit belongs to a decoded field; every operation is known; instruction counts match the headers (a fragment program's counts its constant slots too); each vertex program's input mask matches the inputs it reads; every constant a vertex program reads is a named uniform (by register index, or by a semantic `C<n>`, an array's elements at their offsets) or a literal the compiler made (`internal-constant-N`, variability `0x1007`, its value its default); and every place a fragment parameter's value is patched holds an inline constant. Narrowing the constant field to nouveau's 8 bits on purpose made 110 of the 242 disagree. Unit tests build instructions from the fields, not from the game's bytes.

**What the game uses** (programs): vertex `MOV` 120, `MAD` 102, `MUL` 91, `ADD` 84, `DP3` 72, `RSQ` 71, `MAX` 69, `RCP` 68, `MIN` 67, `SGT` 22, and in three programs each `DP4`, `ARL`, `FLR`, `SLT`, `BRA` with indexing by the address register; condition codes in 30. Fragment `TEX` 106, `MOV` 99, `MUL` 97, `MAD` 81, `ADD` 68, `FENCB` 42, `DP3` 38, `EX2` and `LG2` 31, `FENCT` 31, `DIVSQ` 30, `DIV` 18, `NRM` 16, `MAX` 14; fp16 registers in 75, fixed point in 10, a result scale in 41, condition codes in 27; no flow control.

**The uploaded program is the built one.** The vertex program the game loads for its first draw is the microcode of the Cg program at `0x10201c68`, byte for byte: the programs are found at build time and looked up at run time, as planned.

### Their translation to SPIR-V (`recomp/src/rsx_spirv.*`, `recomp/src/spirv.*`)

**All 242 translate.** `qilin shaders <game> --out <folder>` writes them, as SPIR-V, to `shaders.cpp` (derived from the game: outside the repository), each with its key: a hash of its microcode with a fragment program's inline constants left out, since the game patches those. The renderer finds a program the game uploads by that key; one it doesn't find stops the game.

**The SPIR-V is written by the project's own writer** (`spirv.*`), so building the game needs no shader compiler. Its numbers are from Khronos' published grammar files (SPIRV-Headers, at the tag the Vulkan headers are pinned to), not from memory. SPIR-V 1.3; registers are function variables, loaded and stored around each instruction (the driver's compiler keeps them in registers).

**What a translated program expects of the renderer** is stated at the top of `rsx_spirv.hpp`: vertex constants (468) and a fragment program's inline constants in uniform blocks; the RSX's viewport folded into the position by push constants; outputs and inputs at locations by register number; a texture unit's dimension (2D or cube) from the program's Cg parameters.

**A program's other forms for draw state.** Some of the RSX's state changes what a shader declares, which the renderer can't change in a module: a decoration or a built-in. For those, `qilin shaders` translates a program again in another form (`rsx_spirv.hpp`'s `Variant`), each its own module beside the plain one in `shaders.cpp` (`kSpirv<n>v<form>`) and in the shader table's `variant_spirv` (`shaders.hpp`), made only where a draw could use it. A fragment program that reads a colour has a **flat form** (form 1: `COL0` and `COL1` decorated `Flat`), for `SET_SHADE_MODE` FLAT: 28 of the game's 121. Such a program also has **two-sided forms** (2, and 3 with flat colours: the back colours `BFC0` and `BFC1` read at locations 3 and 4 on back faces, chosen by `FrontFacing`), for `SET_TWO_SIDE_LIGHT_EN`, but only where some vertex program writes a back colour: none of the game's does, so it has none. A vertex program that writes a user clip plane's distance has a **clip form** (form 1: `ClipDistance[6]`, with its capability): plane n's distance is the output `FOGC`'s y, z or w for planes 0 to 2 and `PSZ`'s for 3 to 5 (*a stated reading of NV40's, as Mesa's driver writes them*), and each plane's test is specialisation constant n (0 off, 1 kept where the distance is below 0, 2 where it is 0 or more: the pipeline's state, so one module serves every combination; *with LT a distance of exactly 0 is kept: a stated difference*). None of the game's vertex programs writes one, so it has none; the translation records the planes each program writes (`clip_planes` in the table). Synthetic flat, two-sided and clip forms (`ridgeracer7_shader_forms_test`, `RR7_FORMS_OUT`) pass `spirv-val` and this PC's driver in pipelines. `ridgeracer7_shader_forms_test` holds what each form declares, on synthetic programs; `validate_shaders.py` and `ridgeracer7_shader_check` take every form as they take the plain modules (all 28 pass both).

**The R and H registers are one file.** The NV40 family's fp16 `H` registers are the halves of its fp32 `R` registers (`H2n` and `H2n+1` of `Rn`), and the game's programs show it: every fragment program's register count is at least `max(Rn+1, (Hn+2)/2)` of what it uses, and exactly that in 77 of the 121 (the rest have the minimum, 2). The translation keeps the two views as separate values, which is exact as long as no value crosses between them, and **refuses any program in which one does**: it tracks which view last wrote each quarter of each register and checks every component an instruction actually uses. No program is refused. (A register moved to itself in place, which the compiler emits, is the same bits either way.)

**Found by that check**: `DIV` and `DIVSQ` divide by their second source's *first* component, as a scalar. The game computes a length into one component and divides a vector by it (`DP3R R1.x, R2, R2; DIVSQR R3.xyz, R2, R1`); read component by component, those programs crossed between the views, which is how it showed.

**Stated choices**, to be compared with the console's picture: an output component the vertex program doesn't write is `(0, 0, 0, 1)`'s; with both vertex units at work, the vector unit's result sets the condition codes; a branch's condition is its first component's (refused if its swizzle isn't one component repeated); the fences (`FENCT`, `FENCB`) have no value; fixed point (s1.10) is a clamp to [-2, 2 - 1/1024] and a rounding to 1/1024; an fp16 result is rounded with `OpQuantizeToF16`; the fragment input flag in word 3's bit 31 is no-perspective interpolation (refused if a program reads an input both ways).

**Checked**: unit tests translate synthetic programs and check refusals by name; and **`ridgeracer7_shader_check`** (built with the lifted code) gives all 242 to the local Vulkan driver: a module for each, and a graphics pipeline for each with a partner that writes what it reads. On the owner's PC (NVIDIA GeForce GTX 1080 Ti) **all 242 modules and 242 pipelines are taken.** A driver is lenient, so they are also given to **Khronos' validator**, `spirv-val` (SPIRV-Tools v2026.4, built from source outside the repository; `tools/check/validate_shaders.py`), for the Vulkan 1.3 environment: **all 242 pass**, and a module with a fault put in on purpose (a fragment shader's origin turned to lower-left) is refused. *Still owed: a test of the translation's meaning against a reference, as the lifters have.*
