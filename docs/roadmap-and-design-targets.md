# Ridge Racer 7 (PS3) — Recomp Roadmap & Design Targets

**Guiding principle: efficiency and reliability come first.** Every design choice is judged on whether it makes the game cheaper to run on low-end hardware and whether it fails loudly and predictably instead of silently misbehaving.

The requirements and scope are the same as the other Qilin recomps' (GBTGhoulies--QilinRecomp set them; BeatTheBeat, PunchOutWii and WindWakerHD apply them to Nintendo's consoles), down to the settings menu. Where the PS3 differs, this document says how the same rule applies. Decisions marked **open** wait for the analysis of the game's program; nothing here is assumed about the game that hasn't been read from it or isn't marked as coming from public descriptions.

## Targets
- **Game:** *Ridge Racer 7* (Namco Bandai Games, 2006), the **USA** disc (`BLUS30001`, version 01.02; Redump: "Ridge Racer 7 (USA) (En,Ja)"), recognised by SHA-256 (`elf-analysis.md`). Other regions, later patches and the "3D License Version" are other binaries and out of scope for now.
- **Controller:** the PS3's own (Sixaxis / DualShock 3), from any gamepad SDL knows and the keyboard. **Open:** steering wheels (the program links the USB library, so it probably drives wheels itself: what it expects, and whether SDL's wheels can stand in, is for the analysis).
- **Platforms:** 64-bit Windows, Linux and macOS (Intel and Apple Silicon), on x86-64 or ARM64, with Vulkan. See *Hardware scope* below.
- **Language:** **C++23** throughout (recompiler, generated code and runtime). Minimum compilers: GCC 14, Clang 19, Xcode 16, Visual Studio 2022 17.10.
- **Graphics API:** **Vulkan 1.3, and only Vulkan.** We require the 1.3 core API, and only the optional features and limits that Mesa's v3dv driver on a Pi 4 provides, so one render path works everywhere (MoltenVK on macOS). See *Vulkan baseline* below.
- **Reference:** RPCS3 running the original game is ground truth for behaviour, visuals and audio, as Dolphin and Cemu are for the other recomps. Its code is not copied (`prior-art.md`).
- **Enhancement example target:** 3440×1440 (21:9) at 144 Hz.

## Architecture
- **Game code:** static recompilation, PowerPC (the Cell's PPU) → **generated C++**, compiled AOT by clang/GCC/MSVC for each target. No interpreter, no JIT, and no emulator underneath. Hand-written C++ replaces lifted functions over time (hot paths, bugs, enhancement hooks) through a function override table.
- **SPU code:** the program links SPURS and carries **42 SPU programs** in its data, 209,492 words of code: particle effects, collision, the car's dynamics and the sound core (`elf-analysis.md`). The physics is on the SPUs, so none of this can be put off. The rule is the same as for the PPU: **SPU programs are statically recompiled to C++ too**, each image lifted ahead of time, with no SPU interpreter. An SPU has its own instruction set, 128 registers of 128 bits and a 256 KiB memory of its own, so this is a second decoder and a second lifter. **Open:** how many images, whether any SPU code is loaded from the game's data files and not the program (it must be a closed set found at build time, as shaders must), and whether the game's SPURS use is plain jobs that could be run as native calls.
- **Decoders:** **our own, table-driven**, as in the other recomps, each **verified word by word against GNU binutils** over a sweep of the encoding space in CI and over every word of the game's code. The PPU is not the 750 the Nintendo recomps decode: it is 64-bit, has VMX (AltiVec) and has no paired singles, so the decoder is a new table in the old shape. Reserved bits set and invalid forms decode as invalid. ✅ The PPU decoder (`recompiler-core.md`). ✅ The SPU decoder (v0.6.0): its reference is binutils 2.31.1, the last line with the SPU, which CI builds from the GNU source for the purpose.
- **Symbol naming:** cheapest first: (1) system functions by their own names, from their ids (`prior-art.md`); (2) the C and C++ library functions linked into the program, by matching against the same SDK's libraries if a clean source exists, else by behaviour; (3) everything else stays `fn_<address>`.
- **Register model:** guest registers held in host locals inside each lifted function and synced to a context struct only at call/indirect boundaries: 32 GPRs of 64 bits, 32 FPRs, 32 vector registers, CR fields, XER, LR, CTR, VSCR. No global or thread-local register variables.
- **Calling conventions:** lifted code keeps full register state across calls; ABI recovery only at the boundary with native code, which is every imported function and system call (arguments in `r3`–`r10`, `f1`–`f13` and `v2`–`v13`). Function pointers are **descriptors** (code address and `r2`): an indirect call loads both, and the dispatch table is keyed by code address.
- **Fail loudly:** an undecodable or unsupported instruction is a build error, never a comment; an unknown indirect-call target at runtime traps with its address logged; an imported function or system call with no native code stops the game by name.
- **Control flow:** recursive-descent CFG with resolved switch tables. Function discovery starts from what the program gives: the 14,046 function descriptors and the C++ unwinding tables (`.eh_frame` bounds every function that can unwind), then calls. ✅ Done for the PPU (v0.4.0, `recompiler-core.md`): every word of the code accounted for, the jump tables read through the TOC and the per-file constant tables. **C++ exceptions are real in this game** (932 functions with exception tables, 2,845 landing pads): the unwinder and personality routine are lifted with the rest and find their way by the program's own unwinding tables, which describe guest frames in guest memory, so they keep working; what the lifter must provide is every landing pad as an entry into its function. **The shape** (built after v0.13.1, `recompiler-core.md`, "C++ exceptions"): the guest's unwinder ends by "returning" into a landing pad of a function further up the stack, with the stack pointer moved there, which a lifted `blr` (a C++ `return`) cannot do. So that one return (`__builtin_eh_return`'s epilogue in the lifted unwinder, `add r1,r1,r10; blr`, the only stack adjustment by a register in the program, four times) becomes a host C++ exception carrying the landing pad's address and stack pointer; a function that has landing pads is lifted twice, from its start and from its pads (a switch at the top), and run by the runtime's one `try`, which takes the exception if the pad is one of the function's and the pad's frame is this activation's (its back chain is the stack pointer the activation was entered with), and runs the pads' body, which reads the registers again; otherwise it lets the exception pass. Host unwinding does the popping of host frames that the guest's unwinder did for guest frames. Functions without landing pads pay nothing. ✅ The epilogue's shape is confirmed in this program, and any other is refused by name; 932 functions are lifted so; the worst lifted file's compile goes from 20 s and 708 MB to 33 s and 874 MB, a typical one's by 6% (a `try` in each function would have cost twice the time and memory).
- **Endianness:** the guest is big-endian and every host is little-endian. Guest memory keeps the guest's byte order; each lifted load and store swaps bytes. Vector registers keep the guest's element order, so a vector load is one 16-byte reversal. Structures shared with native code are read and written through big-endian accessors.
- **Lifter efficiency:** CR and XER elimination through dataflow analysis: done within each function (2026-11-28, `docs/recompiler-core.md`, "Lifted code's speed"): flags are locals the compiler drops when dead, a sync site writes back only what changed, and a branch reads the compare that set its bit. Still open: writing back at a call only what the callee reads, which needs the whole program's call graph. Floating point is native `double`/`float`, bit-exact: the `fmadd` family becomes `std::fma`, and `-ffp-contract=off` keeps the host compiler from fusing anything else. VMX in portable C++ on fixed-size arrays that compilers vectorise (no host intrinsics, by the portability rule), each operation proven by the differential test. Flat memory (4 GB host reservation, `base + addr`: the process's addresses are 32-bit).
- **Memory map:** the program at its linked addresses (code at `0x00010000`, data at `0x10000000`, so no relocation is applied); the heap, stacks, the RSX's memory and mapped I/O memory where the system would put them. **Open:** the exact ranges, from the process parameters and the game's memory calls.
- **System software:** a PS3 game is a client of an operating system, as a Wii U game is: every system function is in a library outside the program, reached through the import table (22 libraries, 248 functions here) or by a system call. So the boundary is exact and given: **every import and system call is replaced natively at its API**, and everything inside the program (the game, its engine, the C and C++ libraries, the graphics library's command writers) is lifted. `qilin imports` plus the list of system calls is the runtime's complete to-do list.
- **Threads:** the PPU runs two hardware threads at once and the SPUs six more programs. Guest threads are host threads; PPU threads hold one of two core tokens to run guest code, handed out by priority, as WindWakerHD's scheduler does with three (`lwarx`/`stwcx.` and `ldarx`/`stdcx.` are host atomics). Done after v0.13.1 (`runtime.md`): a token is given up at every wait, preemption happens at calls into the system, a thread kept waiting by guest code that never calls the system runs on a lent token, and waiters are woken in the objects' own orders. SPU work runs on host threads of its own. **Open:** what the game depends on in the scheduler's order (lent tokens in the log say where the model and the game disagree), and its timing model (60 frames a second, by public descriptions).
- **Graphics:** the RSX is driven by a **command stream** the game writes itself: `libgcm`'s command writers are linked into the program (and so lifted), and only its system side (`cellGcmSys`: set-up, memory mapping, flips) is imported. So the RSX is replaced **at the command stream**, as the Wii recomps replace GX at its FIFO: the runtime reads the commands the lifted code wrote and draws with Vulkan. Two parts need real work:
  - **Shaders.** The game ships RSX vertex and fragment programs compiled, not as source. They are translated to SPIR-V **ahead of time**, at build time, from the game's own files: a static recompilation of the shaders, with no shader translator running in the game. ✅ They are a closed set: **242 compiled Cg programs in the program's own data**, 121 vertex and 121 fragment (`data-files.md`). **Open:** fragment programs carry constants patched in place, which the translation must turn into uniforms; whether the 121 and 121 are used as fixed pairs.
  - **Surfaces and textures.** Render targets and textures live in RSX memory the game addresses directly, some of them swizzled or tiled; the renderer's caches follow the console's own rules for when memory changed, never hashing per draw.
- **Films:** the `.pam` files are played through the system's demultiplexer and video decoder (`libpamf`, `libdmux`, `libvdec`), which are imports and so replaced natively. That needs a video decoder on the host. The films are **MPEG-2 video** at 1280 × 720 (one at 320 × 176), three of them with an ATRAC3plus sound stream (`data-files.md`): **Decided (2026-11-22, the owner): FFmpeg's libavcodec**, fetched by CMake and pinned, built with only the MPEG-2 video and ATRAC3plus decoders (LGPL-2.1-or-later, compatible with the project's GPL-3.0). One dependency serves the films' pictures and sound and the music. Writing an MPEG-2 decoder from ITU-T H.262 was the earlier plan; ATRAC3plus has no public specification, which settled it. The game stops at its first film (`cellPamfGetHeaderSize`) until the films are provided.
- **Fonts:** the game draws its text with the system's font library (`cellFont`), from the console's own font sets. Decided by the owner, 2026-11-21: the library is replaced at its API on **FreeType** (what the console's is built on; fetched and pinned), and **the console's fonts are the player's to supply** from a PS3's system software, as the game is: nothing is redistributed and nothing stands in (`runtime.md`). **Open:** hinting, the meaning of the scale and which files make each font set, to be compared with the console's picture.
- **Audio:** sound output (`libaudio`) is a set of ports the game fills with mixed samples, up to 5.1: replaced at its API, output through SDL3 with the other recomps' low-latency work (exclusive mode on Windows, a held queue depth). The music (`BGM.nub`) is ATRAC3plus in 5.1 at 48 kHz and the announcer (`Game_DJ.nub`) is 16-bit PCM (`data-files.md`). The game decodes ATRAC3plus through the system's decoder (`libatrac3plus`, `libadec`), also an import: a native decoder is needed, and the music depends on it. **Decided (2026-11-22): FFmpeg's ATRAC3plus decoder**, the same libavcodec as the films' (above).
- **Input:** `libio`'s pad calls are replaced at their API: buttons, sticks and the pressure-sensitive buttons from SDL3 gamepads (every pad opened and their inputs added up, as the other recomps do) and the keyboard, press-to-bind in the settings menu; the Sixaxis's motion sensors from a pad's own where it has them.
- **Files and saves:** the game's files are read where the player's copy is; nothing is converted offline. Saves and the game's hard-disk data (`cellSaveData`, `cellGame`-style calls in `libsysutil`) go to host folders in the game's data folder. **Open:** whether the game installs data to the hard disk and expects it there.
- **Online:** the program links the PlayStation Network and matchmaking libraries. There is no service to talk to: the runtime answers as a console that is not signed in and has no network, and the online modes are out of scope.
- **Platform layer:** SDL3 (window, events, pads, audio), the Vulkan headers and volk, Dear ImGui for the settings menu, all fetched by CMake at pinned versions and linked statically, as in the other recomps. Keep dependencies to the fewest possible.
- **Portability rules:** no inline asm or host intrinsics in the runtime; ARM64 Linux builds from day one.

## Hardware scope
**Supported: 64-bit hosts with a Vulkan 1.3 driver.** In practice that means:
- **Windows and Linux** on x86-64 or ARM64 with a Vulkan-capable GPU and driver;
- **macOS on Intel and Apple Silicon Macs**, through MoltenVK (Vulkan on top of Metal): any 64-bit Mac with a Metal GPU running macOS 10.15 (Catalina) or later. The runtime (what players run) is built for macOS 10.15 and doesn't use `std::format`, which Apple's libc++ only has from macOS 13.3; the developer tools (`qilin`, the tests) need 13.3;
- **ARM boards** with Vulkan 1.3 drivers, e.g. Raspberry Pi 4 and newer (Mesa v3dv, Mesa 24.3 or later).

**Out of scope:** anything without Vulkan 1.3, 32-bit hosts, and phones and tablets (iOS, iPadOS, Android).

**Low-end reference:** a Raspberry Pi 4–class board, as for the other recomps: what efficiency is measured against, not a floor. The PS3 is a far stronger console than the ones the family started with (a 3.2 GHz processor with two threads and six SPUs, a GPU with programmable shaders, a 1080p picture at 60 frames a second), so whether a Pi 4 can hold the game's own frame rate at a reduced internal resolution is **open** and will be measured, not promised. The Vulkan feature set stays 1.3 core plus what v3dv supports, so the one render path runs wherever the speed allows.

### Vulkan baseline: 1.3
As the other recomps': dynamic rendering, synchronization2, extended dynamic state, timeline semaphores; optional features and limits bounded by v3dv; the features used are checked at start-up and a missing one is a clear message, never a fallback path. Anything an RSX feature needs beyond that is a decision to record here when the analysis shows the game uses it.

## Settings, not platform branches
All enhancements live behind a settings file with presets, as in the other recomps:
- *Original:* the console's own picture and frame rate.
- *Low-end:* reduced internal resolution, no AF, no MSAA.
- *Desktop:* scaled resolution, 16× AF, MSAA, widescreen beyond 16:9, high refresh rate.

**The settings menu is the other Qilin recomps' menu** (Dear ImGui; PunchOutWii--QilinRecomp's `menu.cpp` is the model, WindWakerHD--QilinRecomp's the newest copy): F1 or Esc opens it over the game, which pauses (a controller: Back and Start together); Close and Quit top right; closing saves. Three pages:
- **Controls:** each PS3 controller button's inputs, press-to-bind (*Add* on a row, then the key, the pad's button or a click; an input already bound elsewhere moves over; click an input to remove it); rumble.
- **Display:** full screen (also F11 or Alt+Enter) and which display; the picture's size (whole multiples, fit, or fill) and smooth or sharp; its look (plain or the CRT look, kept for parity though this is an HD game); *Look at the picture*; vsync; the enhancement preset, internal resolution and anisotropic filtering; the graphics device; frame times (F3: frame rate, 1% and 0.1% lows, a frame-time graph, the display's refresh).
- **Game:** the console settings the game reads through `cellSysutilGetSystemParamInt` and `String`: the system language (English or Japanese, this disc's), which button confirms (cross or circle), the console's nickname, the user's name, the time zone. Still **open**: the picture mode the console reports (480p, 720p or 1080p) and the sound output (stereo or 5.1), which the video and audio output functions answer and the renderer would have to follow.

Done (after v0.13.1): the menu and the file, `ridgeracer7/src/menu.*` and `settings.*`, WindWakerHD's adapted. Not offered until the renderer can do them, and shown greyed out: the preset, internal resolution, anisotropic filtering, MSAA. No rumble: the game never sets a controller's motors. Pausing holds the flip, the vertical blank and the sound (`docs/runtime.md`).

Everything is kept in `ridgeracer7.ini` in the game's data folder, `qilin/ridgeracer7` in the per-user application data, with the saves, the pipeline cache and the log (`ridgeracer7.log`, and `ridgeracer7.old.log` from the run before).

## Roadmap
1. **Analysis:** 🔨 started. ✅ the tools find the game however the player holds it and read what the disc gives without decrypting (v0.1.0): PARAM.SFO, the SELF's plain header (the program's segments and sections, the SDK libraries it was linked from), and the loader for the decrypted program with its imports, exports and parameters (`elf-analysis.md`), tested on synthetic files. ✅ the headers of the sound banks and films, and a first survey of the archive (v0.2.0, `data-files.md`): MPEG-2 films, ATRAC3plus music in 5.1, PCM speech, an archive with no directory of its own. ✅ the decrypted program read, with nothing in the loader to fix (v0.3.0): the build's hash, the 22 libraries, the code's profile (151 instructions used), 78 system calls made directly, the 42 SPU programs. **Next:** ids matched to names; the decoder's cross-check over every word of the code; the control-flow pass taught this compiler's idioms until every word is accounted for; the formats inside `RR7.DAT`'s packs and its compression (its directory is read, v0.5.0, and the shaders found in the program); the thread and timing model.
2. **Recompiler core (C++23):** 🔨 started. ✅ the decoders and control-flow passes for the PPU and the SPU (v0.2.0 to v0.7.0, `recompiler-core.md`). 🔨 the PPU lifter: integers, control flow, floating point and VMX lift 14,196 of the game's 14,294 functions and agree with a separate, integer-only reference over 1.3 million runs (v0.10.0). The VMX estimates (`vrefp`, `vrsqrtefp`) are the correctly rounded values, a stated choice (v0.13.0); the PPU's own tables stay **open**. **Open:** VMX's non-Java mode and NaN order, assumed from public descriptions. Then the rest of the lifter (64-bit, VMX), in the shape of the Nintendo recomps'; the SPU decoder and lifter; a differential test of each against an independent reference; coverage with 0 unknown words; every function lifted.
3. **Runtime skeleton:** 🔨 started (v0.11.0, `runtime.md`): the executable builds from the owner's copy, loads the program at its addresses and runs its start-up code as lifted native code, stopping by name at the first system function not provided. To do: the `ridgeracer7` executable built from the player's own copy; the program placed at its addresses; registries of imports and system calls that stop on anything unprovided, naming it and its caller; threads, synchronisation, memory, files; SPURS.
4. **Boot to first frame:** the RSX's command stream on Vulkan, the shaders translated at build time, the first frame presented.
5. **Playable at original spec:** sound, controllers, saves, films; matches RPCS3; tested on low-end reference hardware at every milestone. The window and the settings menu come early, as in WindWakerHD.
6. **Resolution / AF / MSAA:** scaled render targets, with the game's post-processing scaled to match.
7. **Widescreen 16:9 → 21:9:** Hor+ projection, HUD and menus re-anchored, pillarboxing where a scene can't widen.
8. **High refresh rate:** investigate the game's tick model first (the console runs it at 60 frames a second); that decides between interpolation and a faster tick.
9. **Extras:** steering wheels, texture replacement packs, etc.
