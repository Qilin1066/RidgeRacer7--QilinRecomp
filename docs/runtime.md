# The runtime

What the lifted game runs on: `runtime/` (what lifted code compiles against) and `ridgeracer7/src/` (the game's machine). Started at v0.11.0; this page says what exists and how it was checked. At v0.12.0 the game ran as far as graphics initialisation; at v0.13.0 it runs to the start of SPURS.

## Building and running the game

```
powershell -ExecutionPolicy Bypass -File tools\build-ridgeracer7.ps1 -Game <your copy> [-Run]
```

The script builds `qilin`, lifts your copy's program to C++ (`qilin lift <game> --out build-game\gen`), and builds `ridgeracer7` from that. By hand: configure with `-DQILIN_GEN_DIR=<the folder lift wrote>` and build the `ridgeracer7` target. `ridgeracer7 <game>` then runs it.

- The executable holds the lifted code of **your copy's** program, and nothing else of the game: the program's data is read from your copy each time it starts. At start-up it checks that the program it is given is the one it was built from (by SHA-256) and refuses any other.
- The lifted code and the executable are derived from the game: they stay on your PC, in folders the repository ignores.
- The first build compiles 14,294 functions: about 14 minutes on the owner's PC with one compiler at a time (v0.11.0 turns on MSVC's `/MP` for the lifted files). `qilin lift` rewrites only the files that changed, so later builds compile only those.

## The machine (`ridgeracer7/src/machine.*`)

- **Memory.** 4 GiB of host address space reserved in one piece (`rt::AddressSpace`), so a guest address is a host address by one addition; only what the guest has been given is backed by memory, and an access outside it faults. The program's segments go at the addresses they were linked for (code at `0x00010000`, data at `0x10000000`): nothing is relocated.
- **The first thread.** A stack of the size the program's parameters ask for (128 KiB), `r2` from the entry point's descriptor, and the registers the system hands a new process: the arguments in `r3` to `r5`, the thread's id in `r7`, the thread-local image's address and sizes in `r8` to `r10`, the heap's page size in `r12`. *The assignment is read off the start-up code's own use of them (it passes `r7` to `r10` straight to `sys_initialize_tls` and keeps `r12`) and public descriptions.*
- **Calls through a register** (`hooks->call`) look the target up in the table of lifted functions; a target that is no function stops the game.
- **The boundary with the system is exact, and anything not provided stops the game by name.** A PS3 game reaches the system only through its 248 imported functions and its 78 system calls:
  - each import's slot is given a descriptor whose code address is the import's own, in a range of guest addresses where nothing is, so the game's own import stub (which is lifted like any other code) arrives at `hooks->call` with an address that says which import it is;
  - a system call arrives at `hooks->system_call` with its number in `r11`.
  A function or call the runtime provides is run; any other ends the process with one line: its name, its library and id (or its number), and where it was called from. Nothing is answered with a guess.
- **Unlifted functions** (the 2 the lifter doesn't cover yet) exist as functions that stop the game with their reason if called.

## The RSX (`gcm.cpp`, `rsx.cpp`)

The game writes the RSX's commands itself (that code is the game's, and lifted), into a buffer in its own memory which `cellGcmInit` maps for the RSX: 64 KiB of commands in 49 MiB at `0x20100000`. The layout handed out is the console's by public descriptions: the RSX's own memory (249 MiB) at `0xC0000000`, the mapped memory at offset 0, the first 4 KiB kept back, the command buffer in 32 KiB pieces of which the context holds one, and a callback (a function of the runtime's the game can call: `native_function`) that moves to the next piece when one is full.

- **The RSX is a thread** that runs the commands between `get` and `put` in the control register: jumps, calls and returns, and methods with their arguments. A jump to itself is the game's way of holding the RSX, and is waited on.
- **Methods that only set state are kept in a table** (`kState`: the chip's public names for them); the few that act read it. So far the acting ones are the labels (`SEMAPHORE_OFFSET`, `RELEASE`, `ACQUIRE`; `BACK_END_WRITE_SEMAPHORE_RELEASE`, which exchanges two of its argument's bytes as the chip does; `TEXTURE_READ_SEMAPHORE_RELEASE`) and `SET_REFERENCE`. **A method that is neither stops the game with its number**: nothing is skipped. Drawing is not provided yet.
- **Flips** reach the RSX as two commands of the runtime's own (`0xE940`, `0xE944`, outside the chip's methods), put in the stream by `cellGcmSetFlip` and `cellGcmSetWaitFlip` so that they happen in order with the drawing. Waiting for a flip when none is pending does nothing; showing one is not provided yet.
- **The vertical blank** is a thread at 59.94 Hz which calls the handler the game registers, as one of the system's own threads does on a console.
- **Drawing** (`renderer.*`, on Vulkan in the window's GPU). **Guest memory is the truth at every point where the game can look.** Draws are recorded into a batch: a colour surface is uploaded from guest memory when the batch first draws to it and then stays on the GPU; vertices, indices, constants and texels go into one 64 MiB arena. The batch is submitted, waited for and its surfaces written back to guest memory (a flush) before every label or semaphore the RSX writes or waits on, the game's reference mark, a clear (done on the CPU), a flip, and when the RSX has been out of commands for 2 ms (not at once: the game often runs it dry mid-frame, and each flush writes every surface drawn back); the renderer flushes by itself when a draw would sample a surface drawn in the batch, or draw to memory another of its surfaces covers, or the batch is full. So whatever the game reads after the RSX tells it drawing is done is what was drawn. (The first design, which wrote every draw's surface back at once, managed under a flip a second once the game drew real frames.)
- **What keeps it fast** (measured on the title screen with `RR7_SECONDS`, which ends a run after so many seconds, saves its last picture as `frame-0.bmp` and logs where the renderer's time went, with GPU timestamps): surfaces' staging buffers are in host-cached memory (reading uncached memory back took 750 ms a flush); a surface whose guest memory still hashes as it was written back is not uploaded again; only surfaces a draw wrote are copied back; textures stay on the GPU and are decoded again only when a hash of their guest bytes changes, taken once a batch (within one the game can't change a texture the batch drew with: it can't know the RSX is done with it without a label, wait or flip, each of which ends the batch; the texture-cache invalidation, sent before nearly every draw, doesn't change that); depth is D32S8 where the GPU has it (NVIDIA copied D24S8's depth out in 32 ms a surface, D32S8's in 4.5). The title screen went from 26 flips in a minute to about 33 a second; what's left is mostly hashing and the copies back.
- **Depth** (Z24S8 only): the surface is uploaded and written back like a colour surface, depth in a word's top 24 bits and stencil in the low byte, and attached only to draws with the depth or the stencil test on (with both off the RSX writes neither). **Stencil**: both faces' functions, masks, reference and operations (NV30/40's methods `0x328`-`0x364`, OpenGL's values) as Vulkan's stencil state; with the back faces' test off the front's applies to both. In D32S8 depth is the float d / (2^24 - 1): each 24-bit value has a float of its own, so order and what is written back are kept, but a fragment exactly at a stored depth may test otherwise than on the RSX (*a stated difference*). **Culling**: OpenGL's faces and windings, the RSX's anticlockwise taken as Vulkan's since both count y down (*a stated reading*).
- **Textures** (`textures.*`), decoded on the CPU from guest memory at each draw into RGBA8 with every mip level: A8R8G8B8, A1R5G5B5, A4R4G4B4, R5G6B5 (swizzled or linear) and DXT1, 3 and 5, through the unit's remap. Swizzled texels are Morton order, x's bit first; DXT blocks are read as on a PC (little-endian) and interpolate rounding down; 5- and 6-bit channels widen by repeating their high bits: *stated choices*. The sampler comes from the filter, wrap and LOD fields (PSL1GHT's headers name them). The texture cache's control method (`0x1FD8`) has nothing to invalidate.
- **The alpha test** is in the translated fragment programs: two vec4s of push constants (the reference and a quantising scale; which of less, equal and greater pass), so one translation serves with the test on and off. On an 8-bit surface the alpha is compared as stored (rounded to 255 steps): *a stated choice*.
- **Primitives:** points, lines, line strips, triangles and strips directly; fans, polygons, quads and quad strips as triangle lists through indices (a quad a, b, c, d as a, b, c and a, c, d: *a stated choice*).
- **The window's origin** field (`0x1D88` bits 12 to 15): 1 has window y counting down from the top. *A reading from evidence*: PSL1GHT always writes 1 with a negative y scale and its samples draw upright, as the game does; taken the other way round the game's first logo came out upside down. 0 stops the game.
- A draw finds its programs among the translated ones by key (`docs/recompiler-core.md`) and stops the game if one is missing. Vertex arrays are converted to floats from guest memory at each draw; the vertex constants and a fragment program's inline constants (read from its microcode where the game patched them) go to uniform buffers; the viewport is folded into push constants, the RSX's bottom-left window origin turned into Vulkan's top-left.
- **What the renderer refuses, by name:** flat shading, logic operations, two-sided vertex colours, user clip planes, polygon stipple, polygons drawn as points or lines, polygon offset for points and lines, depth formats but Z24S8, cube maps and other texture formats, surfaces other than colour surface A in formats A8R8G8B8 and F_X32, swizzled or antialiased surfaces, indexed draws. Each is the next piece of work when the game reaches it.
- *Stated choices:* the system's start-up leaves the depth surface's context object at the RSX's memory (`0xFEED0000`; the game never sets it); a clear's rectangle is in the surface's own coordinates, and the colour write mask doesn't apply to a clear.
- **SPURS** (`spurs.cpp`) is this runtime's own. A task runs at once on a host thread of its own (`start_spu_task` in `spu.cpp`), `$3` its 16-byte argument and `$4` the taskset's, as the SDK's `main(qword, uint64)` takes them, with **a SPURS kernel of this runtime's in its local store**, as the SDK's code linked into the tasks reads it (below): the instance's address at `0x1C0`, the workload's number in `0x1D0`'s last word, and a context at `0x2D00` (its address at `0x2FB8`): +152 1 (in a task), +184 the taskset's 64-bit address, +196 the kernel's entry `0x2E00`, +208 the DMA tag 31, +212 the task's number (*the tag and +152's value stated choices*). A call through a register to the entry reaches the runtime (`SpuHooks::native_call`, which the lifted code's computed calls fall back to): 0 ends the task, 2 waits until its signalled bit is set (it is moved from running to waiting meanwhile, as the masks' consistency check in `cellSpursSendSignal` requires). A taskset is a workload of its instance, numbered from 0; its first 128 bytes are kept in guest memory (its masks, the instance's address, the workload's number) under the SPU's atomic lock, and every successful atomic put by an SPU program wakes native waiters. *Not as SPURS does it: tasks don't share SPUs or wait for one; no task is swapped out.*
- **The SPURS kernel as the tasks' SDK code sees it** (read off the 41 tasks; `LightBlurFrameMove_r.elf` for the functions). Its local store below `0x3000`, by uses across all tasks: `0x1C0` (156) the
  SPURS instance's address (its first doubleword; the whole quadword must equal a taskset's +0x60), `0x2FB0` (150) a context whose address is the word at `0x2FB8`, `0x170` (78) the copy of `CellSpurs`'s line +0x70 a task
  updates there (the kernel's line buffer is local store `0x100`), `0x1D0` (40) whose last word is copied into an event flag's line, `0x80` (39) whose word at +8 a function returns. The context: +196 the kernel's
  entry (called with `$3` 0 at a task's end, 2 to wait to be signalled), +184 a value a task's start-up asks for, +152 compared with 0 to tell whether the caller is a task, +208 and +212 used in the event flag's wait.
  A taskset's first 128 bytes, as `cellSpursSendSignal` (`0x4c58`) changes them atomically: six masks of one bit per task, task 0 the top bit: +0x00 running, +0x10 ready, +0x20 pending, +0x30 enabled,
  +0x40 signalled (the bit it sets), +0x50 waiting; +0x60 the instance's address (as `0x1C0`); +0x74 the taskset's workload number, for which a woken task's signaller sets `0x8000 >> n` in `CellSpurs`'s line +0x70
  (`0x4bb8`). *Readings of the masks' names from what the function does with them, to be held to the rest of the SDK's code.*
- **Event flags** live in guest memory in the SDK's layout, since the tasks change them themselves (read off `LightBlurFrameMove_r.elf` at `0x46d8`): +0 the event bits, +4 and +6 the PPU's wait mask and mode (0 any, 1 all), +7 set when the PPU is woken and +0x30 the bits it got, +12 the SPU port it is woken through, +14 the direction, +15 the clearing (0: what a waiter gets is cleared). The PPU's wait and the attachment of its queue (made natively, on a free port of the instance) change the line under the lock the SPU's atomic transfers take, so a task's conditional put fails and it reads the line again. The PPU's set (which would signal waiting tasks) stops the game.
- **Films** (`film.cpp`): `cellPamf` reads the header (`docs/data-files.md`); `cellDmux` cuts the program stream into access units on a guest thread of its own (MPEG-2 pictures by FFmpeg's parser), hands them over in the game's stream memory and tells the game through its callbacks; `libvdec` decodes with FFmpeg's MPEG-2 decoder on another, and gives pictures as YUV 4:2:0 planar (Y, U, V) or ARGB (BT.601 or .709, limited range). What the game uses of each, and the layouts it reads, are read off its film player (`0x2d0000` to `0x2d3900`); the file's head comment lists them. *Stated:* a PAMF stream entry's byte `0x12` holds the frame-rate code in its low bits; the stream-type groups 20 (any picture) and 21 (any sound); codec type 0 is MPEG-2; the ES filter ids are this runtime's own. **Sound** (`cellAdec`, ATRAC3plus): frames cut from PAMF's private stream with their 8-byte headers, decoded by FFmpeg on a guest thread of its own, given as interleaved big-endian floats in the system's channel order (L, C, R, Ls, Rs, LFE, read off the game's own reordering; FFmpeg's blocks taken as L, R, C, Ls, Rs, LFE: *a stated reading*). Downmixing is not provided. **Textures** gained B8 (NV40's L8: its byte is in channel B, the only one Mesa's driver reads; a remap reading another stops the game).
- **Tasks made by tasks.** The SDK's SPU-side `cellSpursCreateTask` writes a 48-byte record at taskset + 0x80 + 48 × id (argument, ELF's 64-bit address, context, local-store pattern) and sets the task's bit at +0x20, picking the first id not enabled. After every atomic put an SPU program makes, the runtime looks (`set_spu_atomic_watch`): a taskset's newly marked task is started from its record. The PPU's `cellSpursCreateTask` writes the same record and picks ids the same way.
- **The 2D objects** the game's library puts on subchannels 3 and 5 (its own command headers say which): 3 the 2D surface (`NV3062`), 5 the image from the CPU (`NV308A`), whose words (0xA400 on, padded to an even count) are written into the surface, row by row, after the renderer's batch is written back. The surface's memory objects start on the RSX's memory (*a stated choice*: the game's first inline transfer comes before it sets them, and its offset is mapped nowhere in main memory).
- **Indexed draws** (`DRAW_INDEX_ARRAY`, 16- or 32-bit big-endian indices): the vertices fetched are the range the indices use, rebased. **Primitive restart** splits on the CPU into lists of triangles (strips keep their windings). **Cube maps**: six faces, each with its levels, each beginning on 128 bytes (*a stated reading*); linear ones too. **Polygon offset** (fill) is Vulkan's depth bias. A draw larger than the renderer's arena grows it.
- **The music** (`atrac.cpp`, `cellAtrac` on FFmpeg's ATRAC3plus decoder), as the game's music thread and reader use it (the file comment lists what): the RIFF/WAVE header read from the game's buffer, which is a ring of the file as its reader reads it; the reader is told where to write, how much and which file position to read, back to the frame before the loop's start after the loop's end; a frame decoded a call, trimmed to the pass's samples, as interleaved big-endian floats. Note the game passes (buffer, its size, bytes read), not the order the SDK's names suggest; while the header isn't whole it answers "read size too small" and the game reads more. *Stated:* the delay is `fact`'s last number and loop points count from after it; the channel order is cellAdec's; no second buffer is ever needed.
- `RR7_DRAWLOG=<flip>` (or `busy`: the first frame of more than 300 draws, some to main memory, as a race's) logs one frame's draws, clears and flip, and writes every A8R8G8B8 or Z24S8 surface it drew as `surface-<address>.bmp` and every texture it sampled, decoded as the renderer decodes it, as `texture-<address>.bmp`; `RR7_SCENE_TEST=1` (or `depth`) turns the fragment tests (or only the depth test) off for draws to main memory. Development aids, never ways to play.
- `RR7_QUIET=1` runs headless, with no sound and no controller but `RR7_PRESS`'s, so a test run disturbs nobody at the computer (it needs `RR7_ANSWER`).
- Tiles and zcull regions are speed on a console, not results: their parameters are kept and change nothing. `cellGcmSetTile` stops the game on parameters out of the ordinary, because the library's own answer to them isn't known here.

## Fonts (`font.cpp`)

The game draws its text with the system's font library: it opens one of the console's own font sets (`0x101`, the default gothic set), sets a size, and has glyphs drawn, which it copies into its own buffers itself. (What the calls take and leave was read off the game's own loop around `cellFontRenderCharGlyphImage`.)

- The console's library is built on **FreeType**, and so is this: FreeType 2.13.3, fetched and pinned by CMake.
- **The console's fonts are the player's to supply, as the game is**: the `data/font` folder of a PS3's system software. Sony publishes the system software file (`PS3UPDAT.PUP`) on its support site; RPCS3 installs it (`rpcs3 --installfw PS3UPDAT.PUP`) and leaves a `dev_flash` folder beside itself. `ridgeracer7 <game> --flash <dev_flash>` names it; without the option, an `RPCS3` folder beside the game's is looked in. Nothing stands in for a missing font: the game stops and says what it needs.
- *Stated choices, to be compared with the console's picture:* glyphs are loaded unhinted; "scale pixel" is the em's size in pixels; glyphs sit on whole pixels; font set `0x101` is New Rodin's Japanese font with the extension font behind it. A character the font doesn't have stops the game (the library's answer to that isn't known here).

## SPU threads (`spu.cpp`)

The game hands the system an SPU program (an ELF file in its own memory), makes a group of threads, gives each a program and four arguments, and starts the group. **A thread here is a host thread running the program's lifted code**: `qilin lift` lifts each of the 42 programs, the one to run is found by where its ELF file lies in the game's memory, and a program that was not lifted stops the game (every SPU program must be known when the game is built). A group can be started again after it ends: each start loads the program's segments afresh.

What an SPU program does beyond its own 256 KiB arrives as the lifted code's hooks:

- **Memory transfers** (channels 16 to 24): get and put between the SPU's memory and the game's, singly or by a list, **done at once when commanded**, so every tag is always complete. The atomic pair (get a 128-byte line with a reservation; put it back only if nobody changed it) is done by comparing: *a put succeeds if the line still holds what was read.* That is how a lost reservation shows in everything but a change back to the same bytes, and it is a stated difference from a console.
- **Mailboxes** (28 to 30): a word in from the game, a word out, and the "interrupt" word by which a thread sends one of the game's event queues an event (`sys_spu_thread_send_event`, and with bit 30 `throw_event`, which the game's programs use). *The event's layout (the SPU key, the thread's id, the port and 24 bits of data, the mailbox word) is from public descriptions of the system: to be checked against the game's reading of it.*
- **Stops**: `0x101` ends the group, `0x102` the thread, `0x110` waits for an event from a queue bound to the thread. Any other stops the game with its code, as does a channel or a transfer command not provided.

**The first to run is the sound core**: `bnusCoreSpu.elf`, thread `bnusCoreMain` in group `bnusCore`, started as soon as the sound port is open. (The game numbers the one thread of that group "1": a thread's number is its own, not a place below the group's size, which this runtime first got wrong; the game ignores the error.)

*Not as a console does it:* SPU threads run freely, each on a host thread, with no priorities, as the PPU's do.

## Files (`fs.cpp`, `gamedata.cpp`)

A game names files by the console's mount points, and each is a folder of the host's:

| | |
|---|---|
| `/dev_bdvd` | the disc: the player's copy (the folder holding `PS3_GAME`). Read only |
| `/app_home` | where the program started from: the disc's `PS3_GAME/USRDIR`. Read only |
| `/dev_hdd0` | the hard disk: `dev_hdd0` in the port's data folder (`qilin/ridgeracer7` in the per-user application data, or `RIDGERACER7_SAVE_DIR`), laid out as a console's |
| `/dev_flash` | the system software, if the player gave one. Read only |

A path is kept inside its mount point (`..` can't climb out), and a name under no mount point is "not mounted". A directory's entries come in the names' order, the same on every host. The structures' layout is the SDK's as the game's own code reads it: a file's size at byte 36 of a packed, 52-byte `CellFsStat`. *Times are left at 0 until the game is seen to read them.* The file-system system calls (801 on: the C library's files) are not provided yet.

**Game data** is a folder of the game's on the hard disk (`/dev_hdd0/game/<name>`, described by a `PARAM.SFO` as on a console; `qilin_game`'s reader gained a writer). The utility works through a function of the game's: it is told what is there and answers whether to go on. The layout of what it is told (5,192 bytes; the description at byte 2,144) agrees with the game's own two functions. **The game asks for `BLJS10001`**, the Japanese release's name: the disc is the American one, the program the same. At start-up it only looks (its function answers "cancel"), finds nothing, and goes on.

## When something goes wrong

- **A bad memory access is reported** (`fault.cpp`): the guest address, the thread, and the lifted functions on the stack, found from the host's return addresses. Then the process stops, as for any other unknown. Before this a fault ended the process without a word.
- `qilin lift --pc` makes lifted code note each instruction's address before it touches memory (`Cpu::pc`), and the report then names the instruction. It is slower, so it is for finding faults, not for playing.
- `qilin lift --registers` goes further than `--pc`: the lifted code writes its registers back before every memory access, and the report prints all 32. Slow; it is what found the fault below. `RR7_DUMP=<addresses>` adds 96 bytes of guest memory at each to the report, and `RR7_CALLS=<thread id, or all>` logs every call a thread makes to the system with its arguments and result.
- `RR7_ERRORS` logs every error code the system hands the game (a game may ignore one, and did). `RR7_FILES` logs every file opened and every read.
- `RR7_ANSWER=<1 yes or OK, 2 no, 3 back>` answers the system's dialogs without showing them, and `RR7_PRESS=<button>@<flip>[,...]` holds a button for six flips: for runs with nobody at the controller.
- `RR7_SAVE_FRAME=<n>[,<n>...]` writes each nth flip's picture to `frame-<n>.bmp` in the current folder; a flip's count is logged every 600.
- Two aids in the environment, neither a way to play: `RR7_WATCH=<seconds>` prints what system function each guest thread is inside after that long, and stops; `RR7_RSX_SURVEY` counts the RSX methods not yet provided up to the first flip, without running them, prints the list and stops.

## Where it stops now

After v0.13.0: **nowhere in a 9-minute run: the game is in its first race, its 3D world drawn** (Lakeshore Drive's fly-by: track, buildings, mountains, the music's choice). Its fault: trees and some foliage come out blue. The textures decode right (`RR7_DRAWLOG`'s pictures of them are green): the blue comes from the shading, where a tree's draw also samples a 512 by 128 surface rendered earlier in the frame, a 1 by 1 B8 texture whose remap makes it read as zero, and a 32 by 32 colour lookup (A8R8G8B8, linear). Read since from the programs (no run): the draw's fragment program has at most 512 bytes of microcode and samples units 0-2 as Decal, Hiyori and Shadow, which fits the two 432-byte Cg programs `0x10253b08` and `0x102570f8`. There the colour is the decal times the vertex colour, **plus the Hiyori texture (the 512 by 128 surface, sampled in screen space) times the alpha and a constant** (`HiyoriBias`), then shadow (none: its texture is the zero B8), fog and `ModulateColor`. The saved Hiyori surface is dark blue in its left 128 by 128 and black in the rest, and that is as the game leaves it: it clears the whole surface every frame under a scissor covering all of it, then fills the left quarter with one draw (viewport, clip and scissor 128 by 128) that samples the previous frame's 1920 by 1080 picture, a 256 by 128 surface, the 1 by 1 B8 and the 32 by 32 lookup. Colour order is not the cause: surfaces are A, R, G, B in guest memory both ways (`to_host`, `to_guest`), as textures are read. The tree draw's fragment constants map the screen onto exactly that quarter (0.125, -0.5, 0.125, 0.5), and its Hiyori term is weighted about 0.35: so the Hiyori surface is not where the blue comes from. Nor are the vertex colours (attribute 3, four unsigned bytes, R, G, B, A with alpha 255: near-grey and dark, 2 to 5 of 255). The blue is wider than the trees: fence posts and banner frames come out blue too. Next: the programs those draws use (most are `043d0501`) and the 32 by 32 lookup some of them sample. `RR7_DRAWLOG` gives each draw's fragment constants and each attribute's first vertex. The race is slow (writing surfaces back dominates). The world was black because the game's clears cleared nothing: it never sets the clear's rectangle, which the system's start-up must leave covering everything (`rsx.cpp`), so its depth stayed at 0 and every depth test failed.

### A fault on the way, and what it was

Before that, the game faulted in its own code (`0x13bd38`): it was going over a table from one pack and found another pack's bytes there. Two faults of this project's, neither the lifter's:

- **`sys_memory_allocate` gave two packs the same memory.** Its first-fit search rounded the candidate address up to the page size asked for; with blocks of both page sizes in the list that could pass the next block's start, and an unsigned difference then looked like a huge gap. (The game allocates each pack's buffer with 64 KiB pages among 1 MiB ones.)
- **The tools had every pack's and file's name one record off** (`docs/data-files.md`), so the game's own, correct, loads looked wrong (`TextFr` for `TextEn`) and sent the search the wrong way for a while.

What found it: registers at the fault (`--registers`), the game's run-time table of pack records dumped beside the tools' reading of the same bytes, and the call trace of the loader thread.
